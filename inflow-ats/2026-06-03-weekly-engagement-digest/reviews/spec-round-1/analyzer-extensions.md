# Analyzer Extensions — Round 1

## Findings

- F1 [MED] `load_base_ids` branching — spec line 143 says "If `organization_user_id` is nil -> all of the organization's jobs (current behavior)." Verified: the current `load_base_ids` (analyzer line 47-51) uses `@organization.jobs.select(:id)`. The branching description is accurate. The spec also says `@job_application_ids` and `@candidate_ids` "are derived from `@job_ids` as today" — but today they are derived from `@organization.job_applications` and `@organization.candidates` (line 49-50), NOT from `@job_ids`. For the org-wide case this is equivalent (organization has_many :jobs, and the downstream chains match). But for the org_user-scoped case, the spec needs to be explicit that `@job_application_ids` must be re-derived from the scoped `@job_ids` (or from `org_user.job_applications`) rather than using `@organization.job_applications`. The current spec wording "as today" could lead an implementer to keep the organization-level derivation, which would bypass the per-user scoping. Downgrading from HIGH because the spec's next sentence ("Note `OrganizationUser` also already exposes `job_applications`... through that same chain") provides the hint, but the primary statement is misleading.

- F2 [MED] `ChannelMessage` query — spec line 152 says "Joins `ChannelMessage` through `Channel` to filter by `@job_application_ids`." Verified: `Channel belongs_to :job_application` (channel.rb:6), `ChannelMessage belongs_to :channel` (channel_message.rb:9). The join path exists. The `sent_by` enum values in the spec (`:sent_by_user`, `:sent_by_organization`, `:sent_by_candidate`) match channel_message.rb:27-32. Also present is `:sent_by_system` (value 0), which the spec does not mention. System messages would be excluded from both `messages_sent_total` (which counts user + organization) and `messages_received` (which counts candidate only). This is correct by omission — system messages are neither sent by a human nor received from a candidate. No action needed, just noting for completeness.

- F3 [LOW] The spec says the analyzer returns "four counts" for messages (line 153-158). The existing `candidate_management_metrics` method (analyzer line 144-151) returns a hash of sub-hashes with `:count` and `:most_recent` keys. The new ChannelMessage query will need to fit into this same structure or the `build_result` method (analyzer line 344-428) will need updating. The spec does not address how the new message counts integrate into the `build_result` output hash. This is an implementation detail but worth noting — the implementer needs to decide whether the message counts go inside `candidate_management` or as a new top-level key.

## Amendments Applied

None required — F1 is MED (the spec's Note sentence provides the necessary hint, and the implementer reading the code will see the derivation chain). F3 is LOW (implementation detail).
