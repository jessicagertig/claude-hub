## Findings

- F1 [BLOCKER — resolved by spec amendment, no redesign] SPEC.md §5.6 placed the D12 identify+track inside `showEmailConfirmationBannerIfApplicable`, which runs from `Auth.tsx`'s mount `useEffect`. **As specced, the event would never fire in production.** Mechanism, verified in source: the confirmation redirect is a full page navigation → the whole tree mounts in one commit ( `/auth` is not gated behind the `me` query: `useGetMe` is `enabled: false` on unauthed routes and a disabled react-query v3 query is idle, so the `Switch` renders immediately) → React flushes child effects before parent effects → `Auth.tsx`'s mount effect runs BEFORE `PostHogProvider`'s `posthog.init` effect → `getPosthog()` returns null → `identifyUser`/`trackEvent` take their skip paths silently. Corroborating existing behavior: `PageviewTrackerInner`'s first-load `$pageview` is skipped by the same ordering. The analog identify (`AppAuthRouter.tsx:168`) only works because its effect re-fires when the async `me` query resolves — `Auth.tsx`'s mount effect has no such re-fire. / Fix applied: §5.6 rewritten — the banner path is unchanged; a second `useEffect` with deps `[emailConfirmed]` fires the guarded identify+track on the re-render `setEmailConfirmed` schedules, which runs after the initial effect flush (i.e., after `posthog.init`). Fires exactly once per landing (state transitions false→true once). D12's moment, event name, file, and payload are untouched — this is wiring, not decision change.
- F2 [MED] §5.6 guard-scope ambiguity: the both-params-present guard was written around the identify only; `trackEvent("email_verified")` read as unconditional. A stale bookmarked `/auth?email_confirmed=true` without `id`/`email` would fire an anonymous `email_verified`, inflating the funnel's step 3. / Fix applied (folded into the §5.6 rewrite): NEITHER call fires unless both params are present.
