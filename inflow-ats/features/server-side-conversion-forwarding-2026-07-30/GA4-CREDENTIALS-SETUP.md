## 2. Step 0 — first, find out whether a GA4 property already exists

**This is the branch point. Do this before anything else.**

The stake: our conversion payload already carries a `ga_client_id` value read from the browser `_ga` cookie, and the Measurement Protocol requires `client_id` in the body, where it "should match the ID generated by the Google Analytics tag on your website" ([sending-events]). Google also states outright that the Measurement Protocol augments browser tagging rather than replacing it, and that "You must use tagging (gTag, Tag Manager, or Google Analytics for Firebase) to use this protocol" ([protocol-ga4]) — so a GA4 property with a web data stream covering the signup domain must already be running and tagged for that captured value to exist at all and to mean anything on the receiving end.

**Permission required before you start, not just in Path A: Editor or above on the Analytics account, at the property level.** Reading a stream's measurement ID in 2c requires it ([12270356]), as does finding the Google tag ID ([9539598]) and generating an API secret ([9814495]). Google does **not** document what insufficient permission looks like — whether **Data streams** is absent from the Admin menu, whether the stream row is unclickable, or whether the details panel simply omits the ID. Marked **unverified**. If **Data streams** or the stream details are not reachable, **stop and escalate — do not read that as "no stream exists."**

### 2a. List the accounts and properties you can see

1. Open Google Analytics.
2. Use the **property selector** in the top-left corner of the UI to see the accounts and properties you have permission for ([10252712]).
3. Pick the property you want to inspect. Note: an **Admin** deep link opens the last property you accessed, so change it with the property selector rather than trusting whatever loads ([12270356]).

### 2b. List that property's data streams

1. Click **Admin** (lower left).
2. Under **Data collection and modification**, click **Data streams** ([9304153], [12270356]).
3. Select the **Web** tab ([12270356]).
4. You now see every web data stream on that property. **An empty list does not mean "no web stream exists."** It can also mean you are signed in to the wrong Google account, or that you were never granted access to the property that owns the live tag. Write down what you see (including "empty") and **continue to 2c and 2d — do not jump to Path B here.** 2d is the only step that can tell those cases apart, and it decides the Path B branch.

### 2c. Read each stream's own measurement ID

1. Click the web data stream.
2. The measurement ID is in the **first row of the stream details** ([12270356]). It starts with `G-` ([12270356], [sending-events-gtag]).
3. Write down which stream name maps to which `G-` ID.

### 2d. Answer "which data stream set the `_ga` cookie on app.polymer.co"

The join is the `G-` ID. The tag installed on the site is what writes the cookie: "Google Analytics stores a client ID in a first-party cookie named `_ga` to distinguish unique users and their sessions on your website" ([11593727]), and `_ga` is the cookie "Used to distinguish users" ([11397207]).

**This subsection's page-source test only works for a raw gtag.js install.** Google supports three tagging routes — "You must use tagging (gTag, Tag Manager, or Google Analytics for Firebase) to use this protocol" ([protocol-ga4]) — and the other two do not put a `G-` ID in page source. Read the whole subsection, including the branches below, before concluding anything.

Google's own gtag.js snippet carries the ID in two places — the script `src` and the `config` call ([gtagjs-install]):

```html
<!-- Google tag (gtag.js) -->
<script async src="https://www.googletagmanager.com/gtag/js?id=TAG_ID"></script>
<script>
  window.dataLayer = window.dataLayer || [];
  function gtag(){dataLayer.push(arguments);}
  gtag('js', new Date());

  gtag('config', 'TAG_ID');
</script>
```

So:

1. Load `app.polymer.co` in a browser and view the page source.
2. Look for a `googletagmanager.com/gtag/js?id=` value and a `gtag('config', ...)` value. **Four things you may find, and only the first is the simple case:**
   - **a `G-` string** — that is the GA4 tag ID the site is sending to. Go to step 3.
   - **an `AW-` string** — the Google tag ID "starts with 'G-' or 'AW-'" ([9539598]); `AW-` is a Google Ads destination. This is **not** evidence that no GA4 stream exists — one Google tag can be connected to multiple destinations ("you can use the Google tag across your entire site and connect the tag to multiple destinations", [gtagjs-install]), so the GA4 `G-` ID may simply not be the id in the `src`. Go to **2d-fallback** below.
   - **a `GTM-XXXXXXX` container reference and no `G-` at all** — the site is tagged through Google Tag Manager, which is a supported tagging route ([protocol-ga4]). The GA4 measurement ID lives **inside the container's GA4 configuration tag**, not in the page source, and must be read there. Go to **2d-fallback** below.
   - **nothing at all** — a React app that injects its tag at runtime shows nothing in raw view-source. Go to **2d-fallback** below.
3. Compare the `G-` string, character for character, against the measurement IDs you listed in 2c. The stream whose measurement ID matches is the stream that set the `_ga` cookie on that domain.
4. **If a `G-` string was found and matches no stream you can see**, there are three explanations and the doc cannot tell you which: (a) the `G-` ID belongs to a property you do not have access to; (b) it belongs to no live property; (c) you are signed in to the wrong Google account. **Stop and resolve that before we send anything — do not go to Path B.** Path B stands up a *second* property, and every historically captured `ga_client_id` would be orphaned against the new stream.

**2d-fallback (the not-found branch): what we already know about our own case.**

Our app layout does **not** carry a raw gtag.js snippet. `app/views/layouts/application.html.erb` loads the Google Tag Manager container **`GTM-N6H844WJ`** (lines 30–37 and the `<noscript>` at line 120), wrapped in `unless Rails.env.test?`. Grepping `app/`, `config/`, and `public/` on branch `server-side-conversion-events` finds **no first-party `G-` measurement ID anywhere** — the only `G-` strings in the repo are the placeholder `G-0000000000` in `AccountIntegrationsGoogleAnalytics.tsx` (a customer-facing field for an org's own job-board tracking ID) and its compiled copies in `public/packs/`. The job board layout still carries a Universal Analytics `UA-129130323-4` tag, which is sunset.

So **the page-source test in step 2 will find `GTM-N6H844WJ` and no `G-` ID**, and that result means "read the ID out of the GTM container," **not** "no live property." Path B is only correct once the container has been checked and shown to contain no GA4 configuration tag.

**Unverified, not corpus-backed — do not treat these as doc-stated:**

- The click path *inside* Google Tag Manager to read a GA4 configuration tag's measurement ID was not researched and is not in our source corpus. Someone with GTM access needs to open container `GTM-N6H844WJ` and read it.
- Reading the `G-` ID out of the browser's network requests (the GA4 collection hit and its `tid` parameter) is a commonly cited fallback but appears on **no page in our source corpus**. Not stated here as fact.
- The `_ga_<container-id>` cookie exists and is "Used to persist session state" ([11397207]), but **no Google page we fetched states that the `<container-id>` portion equals the measurement ID's suffix.** Do not derive the `G-` ID from that cookie name.
- Inspecting the rendered DOM in DevTools rather than raw view-source is an ordinary browser action, not a Google-published check — same category as the view-source step itself.

Why the comparison is the right test: Google states the measurement ID "acts as a critical link, connecting your website to the corresponding data stream" and "ensures that the data from your site is sent to the right location" ([12270356]), and that for one user/session across pages, "The tag on each page must use the same tag ID (i.e., the same 'G-' ID) from the same web data stream" ([10071811]).

**Unverified / not documented, flagged deliberately:**

- Google does not document viewing page source or inspecting `document.cookie` as a verification procedure. Steps 1–2 above are ordinary browser actions, not a Google-published check.
- Google does **not** currently document the internal structure of the `_ga` cookie value anywhere reachable (the `GA1.1.x.y` layout is not stated on any current page — the page that historically carried it, the analytics.js `cookies-user-id` devguide, now 404s with a Universal Analytics sunset notice). What *is* documented: the Measurement Protocol accepts the **full value of the client ID cookie** as a legal `client_id` — "Send the full value of the cookie" ([reference-gtag]). So parsing the cookie into segments is not required by the docs.
- Google does **not** state whether a `client_id` captured on one property/stream is valid when sent to a different property/stream. No page fetched says it is accepted, and none says it is rejected.
- Google does **not** state what GA4 does with an unrecognized, malformed, or fabricated `client_id` — no documented error, no documented drop behavior.
- **A missing `_ga` cookie is not automatically a fault.** Google states outright that "Analytics doesn't store the client ID when analytics storage is deactivated through Consent Mode" ([11593727]). So a signup with no `ga_client_id` on the payload can be a correctly-behaving consent-denied visitor, not a broken tag.

## 3. Path A — a property already exists

You have a property with a web data stream whose measurement ID matches the tag running on the signup domain.

**Permission required for both halves: Editor or above on the Analytics account, at the property level** ([12270356], [9814495]).

### 3a. Copy the measurement ID

1. Click **Admin** (lower left).
2. Under **Data collection and modification**, click **Data streams** ([12270356]).
3. Select the **Web** tab ([12270356]).
4. Click the web data stream ([12270356]).
5. Copy the **Measurement ID** from the first row of the stream details ([12270356]) — the **Stream details** panel ([sending-events-gtag], [9539598]).

### 3b. Create the Measurement Protocol API secret

Google's support page and developer doc give the same sequence with slightly different capitalization; both are reproduced here ([9814495], [sending-events-gtag]):

1. Sign in to Google Analytics ([9814495]).
2. In **Admin**, under **Data collection and modification**, click **Data streams** ([9814495]).
3. Click **Web**, then click the web data stream ([9814495]).
4. In the web data stream details, click **Measurement Protocol API Secrets** ([9814495]). The developer doc writes this label lowercase — **Measurement Protocol API secrets** ([sending-events-gtag]). Which capitalization the live UI uses is **unverified**.
5. If necessary, review and accept the **User Data Collection Acknowledgement** ([9814495]). Whether this is a one-time per-property acceptance or per-stream is **not stated** by Google — the page says only "If necessary."
6. Click **Create** ([9814495]).
7. Enter a **nickname** for the secret, then click **Create** ([9814495]). The nickname is a required step, not optional.
8. Click the copy icon to copy the secret ([9814495]). The developer doc names the field **Secret value** ([sending-events-gtag]).

Limits and management:

- Maximum **10 API secrets per data stream** ([9814495]).
- A secret is deleted from the same screen via **Delete** ([9814495]).

### 3c. Can the secret value be re-read later?

**Not stated by any Google support page.** answer/9814495 only says to click the copy icon after creation; it makes no claim about one-time versus persistent display. The only signal is indirect and API-side: in the Admin API, `secretValue` is an **Output only** field on a resource that exposes `get` and `list` methods ([admin-api-secrets]), which implies the value is readable after creation — but that is the API, not the UI. Marked **unverified**.

**Operate as if it is shown once: copy it at step 8 and paste it somewhere safe before leaving the screen.**

### 4c. Install the tag — this is not optional for our use case

Creating a stream generates a code snippet you add to the site, and "Data is collected from the time you add the code" ([9304153]).

**Where to get the snippet:** in the stream's **Stream Details** panel, click **View tag instructions** ([9304153]).

**The `TAG_ID` placeholder is not literal.** The snippet reproduced in 2d above ships with `TAG_ID` in both the script `src` and the `gtag('config', ...)` call ([gtagjs-install]) — both occurrences are replaced with this stream's `G-` measurement ID.

**Placement:** paste the entire Google tag immediately after the opening `<head>` tag on every page you want to measure, and do not put more than one Google tag on a page ([9744165], [gtagjs-install]).

**Who does this:** pasting a snippet into every page is a change to `app/views/layouts/application.html.erb` in the source repo — an engineering change on a branch, not a GA admin action. Note that layout currently loads Google Tag Manager (`GTM-N6H844WJ`, see 2d), so the alternative is adding the GA4 configuration tag inside that container instead, which is a GTM change and needs no repo change at all. **Decide which before anyone edits anything** — "Don't add more than one Google tag to each page" ([9744165]).

Data collection may take **up to 30 minutes** to begin ([9304153], [9744165]).

Until that tag is live on the signup domain, no `_ga` cookie exists there, so there is no browser-generated client ID for our server-side send to match: the client ID is stored "in a first-party cookie named `_ga`" ([11593727]), written by the on-site tag ([11397207]).

### 4c-check. Confirm the tag is actually live before rejoining Path A

The 30-minute figure is an elapsed-time statement, not a check. Verify:

1. Load the tagged site in a browser.
2. In the property, open **Reports > Realtime** ([verify-implementation]).
3. Look for your own visit. "Events typically show up within a few seconds" ([verify-implementation]).

**If nothing appears in Realtime after the 30-minute window, the tag is not installed correctly. Stop — do not hand over credentials for a stream that is not collecting.** Handing them over first means the misinstall is discovered after the server-side sender is already pointed at it.

### 4d. One stream or two — marketing site plus app subdomain

What Google actually says:

- "In most cases, you should use a single web data stream to measure the web user journey. To ensure consistent user and session reporting for web journeys that span domains, use a single web data stream combined with cross domain measurement." ([9679158])
- Recommended maximum is **3 data streams per property**: one web stream plus one iOS and one Android app stream ([9679158]). No hard numeric limit is published.
- Subdomains of one primary domain "can all be measured in the same Google Analytics property … automatically" ([10607999]). **Caveat: that page is labeled `[Legacy]` (a UA→GA4 migration reference), so it is the weakest source cited here.**
- No official page names the marketing-site / app-subdomain case explicitly. Marked **unverified**.

Consequence to accept if you use one stream: identical page paths on different subdomains display as one page in reports, separable only by adding the hostname via report customization ([10607999]).

**Why the single-stream recommendation holds across two domains:** cross-domain measurement is what carries the identity over. "The cookies retain the same IDs as they are passed from one domain to another via a URL parameter (`_gl`) when the user navigates between domains through a link or a form, and as a result, Analytics identifies just one user and one session" ([10071811]). Without it, "new cookies with new IDs are created for each domain a user visits" ([10071811]) — a visitor who lands on `polymer.co` and signs up on `app.polymer.co` becomes two users with two client IDs, and the `ga_client_id` we capture at signup is not the one the ad click was attributed to.

**Click path to configure it** ([10071811]):

1. **Admin** > **Data collection and modification** > **Data streams**.
2. **Web** > click the web data stream.
3. **Configure tag settings** (at the bottom of the stream details).
4. **Settings** > **Configure your domains**.

**Editor or above on the Analytics account is required to set up cross-domain measurement, and you can create up to 100 conditions** ([10071811]).

### 4e. The cross-subdomain `_ga` cookie consequence — flagged

The gtag `cookie_domain` parameter defaults to `'auto'`, which sets the analytics cookie at eTLD+1: "https://example.com would use example.com for the domain, and https://subdomain.example.com would also use example.com for the domain" ([config-reference]).

Applied here, with the default in place, `polymer.co` and `app.polymer.co` both write the analytics cookie on `polymer.co` — one cookie, one client ID, shared across both. **The consequence sentence ("therefore they share the same `_ga` cookie and client ID") is my inference from the documented `'auto'` default; Google does not state it as a `_ga` sentence anywhere.** Marked **unverified**.

Two related documented points:

- If subdomains end up on **different** cookie domains, self-referrals appear, and Google's stated fix is to "Check your cookie domain settings in your measurement code to be sure that all subdomains in a domain are using the same cookie domain" ([10071811]).
- The default cookie name is the literal `_ga` ([11593727], [11397207]), but `cookie_prefix` exists and prepends a prefix to the Analytics cookie names ([config-reference]) — so any code reading the cookie must not blindly assume `_ga` if a prefix was ever configured.

Once the stream exists and the tag is confirmed live by the Realtime check in **4c-check**, go back to **Path A** for the two values.

## 5. What to send back

**Do not send us the API secret.** It goes straight from the GA admin screen into your `.env` — it never needs to pass through us, and it must never appear in client-side code ([sending-events-gtag]).

Send us only:

1. The **measurement ID** (`G-XXXXXXXXXX`).
2. The **stream name** and **property name** it came from.
3. The `G-` ID you found in 2d for `app.polymer.co` — or "GTM container, no `G-` in page source," or whatever you actually found. If it differs from the stream's ID, say so: that is a mismatch we must resolve before sending anything.

**You add both to `.env` yourself. We never edit that file.** The two lines:

```
GA4_MEASUREMENT_ID=G-XXXXXXXXXX
GA4_API_SECRET=<the Secret value you copied>
```

**Neither value can be validated by any HTTP response — transcribe them carefully.** Google states it twice: "The validation server does not verify `api_secret` or `measurement_id` values. Carefully review those values to make sure they are correct" ([validating-events-gtag]), and "The Measurement Protocol returns a `2xx` status code if the `HTTP` request is received. The Measurement Protocol doesn't return an error code if the payload is malformed, or if the data is incorrect or not processed by Google Analytics" ([reference-gtag]). A single wrong character produces a clean `2xx` and clean debug output, and the event silently never lands. Compare both values character for character against the admin UI, and confirm only by seeing an event arrive in DebugView or Realtime — see §9 of `GA4-MEASUREMENT-PROTOCOL-REFERENCE.md` for that procedure.
