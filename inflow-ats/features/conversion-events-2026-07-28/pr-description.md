## Summary

Attribution, end to end — capture at signup, through to the conversion events that carry it.

1. **Ad platform identifiers are captured at signup.** Google, Meta, LinkedIn, AdRoll and Google Analytics values, read from URL params (`gclid`, `fbclid`, `li_fat_id`, `adct`) and first-party cookies (`_gcl_aw`, `_fbp`, `_fbc`, `_ga`, `_ga_*`, `__adroll_fpc`), persisted onto `users` through all three account-creation paths. `organizations` gets the same thirteen columns, copied off `current_user` at org creation rather than re-read from the browser.
2. **`subscription_events` becomes the main-plan domain-event ledger.** Every subscription conversion, upgrade, cancellation and trial conversion is recorded server-side from Stripe, so it is captured accurately every time rather than dropped like browser events, and carries the attribution that produced it. That is what makes campaign-to-revenue reporting possible. PostHog is the first destination. Other conversion APIs can now be added easily, since the major scaffolding required to support them is implemented.
3. **The signup funnel is now fully instrumented, end to end.** Every step is tracked — signup, email verification, name submission, organization creation — across all three routes in, email, magic link and Google SSO, so drop-off can be measured at each stage rather than inferred. Every step also separates organization owners from invited users, because only owners are conversions — someone joining an existing organization by invitation is not an acquisition, and counting them inflates the funnel and distorts every rate in it. `originally_signed_up_as_owner` is set on the person so the whole journey can be filtered to real conversions. This work completes that set: signup itself was the last step still emitting a single undifferentiated event, and the unreliable browser-side signup event is gone.
4. **Internal traffic to the marketing site is tagged.** `INTERNAL_UTM_PARAMS` appends `utm_source=polymer_app&utm_medium=internal` to 19 outbound links to polymer.co and help.polymer.co, so in-app referrals are distinguishable from acquisition traffic.
5. **UTM parameters and referral source are stored in our own database.** `utm_source`, `utm_campaign`, `utm_data` and `internal_ref` are read off the landing URL at signup and persisted on both the user and the organization, alongside the ad platform identifiers above. That makes our own database the point of truth for where a customer came from — queryable directly, independent of PostHog or any ad platform's own reporting — so we can answer where new users actually come from rather than trusting whichever dashboard is measuring its own performance.

Two schema migrations and one Stripe-calling data migration run at release. 56 RSpec files are deleted net against production; nothing under `spec/` is added.

## What changes

### Attribution capture at signup

- `users` and `organizations` now carry the same thirteen attribution columns: `utm_source`, `utm_campaign`, `utm_data`, `internal_ref`, `adroll_click_id`, `google_click_id`, `adroll_first_party_cookie`, `ga_client_id`, `ga_session_id`, `fbclid`, `fbp`, `fbc`, `li_fat_id`. All nullable, no indexes, no model validations, no length constraints.
- New exports in `app/javascript/shared/lib/utils.js`: `adPlatformQueryParams(search)` (reads `gclid`, `fbclid`, `li_fat_id`, `adct`), `adPlatformCookies()` (reads `_ga`, all `_ga_*`, `_gcl_aw`, `_fbp`, `_fbc`, `li_fat_id`, `__adroll_fpc`), and `adPlatformIdentifiers(search)` merging both. Cookie parsing splits on the first `=` only, matches the name by exact equality, and treats a present-but-empty value as absent. `sanitizeTrackingValue` gained a `maxLength` argument; ad-platform values truncate at `ATTRIBUTION_IDENTIFIER_MAX_LENGTH = 1024`, utm/internal_ref stay at 255.
- The `adct` → `adrollClickId` branch was removed from `sanitizeTrackingParams` and now lives in `adPlatformQueryParams`. Both existing callers (`SignupForm.tsx`, `AuthForm.tsx`) were updated, so there is no regression today; a future caller of `sanitizeTrackingParams` alone would silently lose `adroll_click_id`.
- In `SignupForm.tsx` and `AuthForm.tsx`, the `?gclid` and `?li_fat_id` URL params take precedence over the `_gcl_aw` and `li_fat_id` cookies. Values are captured once into `React.useState` at mount.
- All three account-creation paths persist the eight new fields: `Api::V1::RegistrationsController#sign_up_params` permits them (`#create` passes the permitted hash into `build_resource`), `#magic_create` assigns them explicitly in both `user_params` branches, and the Google SSO path carries them as hidden inputs in `GoogleSSOButton.tsx` (each guarded by `typeof x === "string" && x.length > 0`), through `allowed_keys` in `config/initializers/omniauth.rb`, into `Api::V1::Users::OmniauthCallbacksController` and `User.from_omniauth`, whose signature gained eight keyword args assigned inside the new-user block only.
- `Api::V1::OrganizationsController#create` copies all thirteen values off `current_user`. `:google_click_id` and `:adroll_first_party_cookie` were **removed** from the `organization_params` permit; `OrganizationForm.tsx` dropped its `useCookieValue("_gcl_aw")` / `useCookieValue("__adroll_fpc")` reads and now sends only `{ name, heardAboutUsFrom }`. `useCookieValue` itself is unchanged and still used by `useReferrerCookie.ts`.
- Nothing exposes these columns: no serializer, no API response.
- Note: `ga_session_id` stores a concatenated string of every `_ga_*` cookie (`_ga_ABC=GS1.1…; _ga_DEF=GS1.1…`), not a bare GA4 session id.

### subscription_events as a main-plan ledger

- `event_type` enum is now `pending: 0, assigned_free_plan_on_creation: 1, assigned_free_plan: 2, converted_to_paid: 3, canceled_subscription: 4, downgraded_to_free: 5, upgraded_plan: 6, downgraded_plan: 7, trial_started: 8, trial_converted_to_paid: 9`. Production's mapping started at `assigned_free_plan_on_creation: 0`, so inserting `pending: 0` renumbers every value by one. `validates :event_type, presence: true` was removed; the new column default of 0 supplies `pending`.
- New `enum billing_interval: { none: 0, monthly: 1, yearly: 2 }, _prefix: true`, set from `price.recurring.interval` by `CreateSubscriptionEventFromStripe#billing_interval_for`. Rows created via `CreateSubscriptionEvent` and all backfilled rows keep `none`.
- `SubscriptionEvent#handle_after_commit_on_create` (now public) does three things on every created row: calls `resolve_from_plan` when `from_plan` is nil, which issues `Stripe::Invoice.list(customer:, limit: 20)` and possibly `Stripe::Subscription.retrieve` synchronously and writes the answer back with `update_columns`; branches on `event_type` for Discord and `$set` person properties; then enqueues `PosthogTrackJob.perform_later(organization.owner.id, event_type, event_properties)`. `assigned_free_plan_on_creation`, `assigned_free_plan`, `downgraded_to_free`, `downgraded_plan` and `pending` hit the `else return` and send nothing.
- PostHog event name is the `event_type` string. `SubscriptionEvent#posthog_properties` sends `amount` (cents / 100.0), `stripe_subscription_id`, `stripe_customer_id`, `from_plan`, `to_plan`, `billing_interval` and all thirteen attribution values, each resolved by `attribution_value(owner_value, organization_value)` — owner's user value first, organization column as fallback — then `.compact`ed. `Posthog::Track#default_properties` still merges `email`, `organization_id`, `organization_name`, `plan`. `$set`: `trial_started` → `is_trialing: true`; `trial_converted_to_paid` and `converted_to_paid` → `is_paying: true, is_trialing: false`; `canceled_subscription` → `is_paying: false, is_trialing: false`; `upgraded_plan` → none.
- Discord ownership moved. `Discord::NotifyFreeTrialStartedJob` and `Discord::NotifyTrialConvertedToPaidJob` are no longer enqueued from `Organization#handle_subscription_status_change_after_commit`, and `Notification::PaidSubscriptionDeletedJob#discord` was deleted entirely. All three now fire only from `SubscriptionEvent#handle_after_commit_on_create` (`NotifySubscriptionDeletedJob` additionally gated on `organization.subscription_canceled_at.present?`). The Slack side is untouched: `Notification::FreeTrialStartedJob`, `Notification::TrialConvertedToPaidJob` and `Notification::PaidSubscriptionDeletedJob#slack` still fire from their original trigger points. `Discord::NotifySubscriptionPlanChangedJob` is unchanged.
- New `CreateSubscriptionEventFromStripe` (176 lines) classifies from the Stripe object, not `organization.plan`. Guards: `return unless organization`, and `return if invoice.amount_paid.to_i <= 0`. `subscription` → `canceled_subscription` (`from_plan: organization.plan`, `to_plan: nil`, `amount: nil`). `invoice` by `billing_reason`: `subscription_create` → `converted_to_paid` (`from_plan: nil`); `subscription_update` → `converted_to_paid` when the negative-amount line's plan is nil or contains `free`, `upgraded_plan` when `SubscriptionEvent.upgrade_detected?`, otherwise no row; `subscription_cycle` → `trial_converted_to_paid`, but only when `invoice.period_end - invoice.period_start <= 24.days` **and** a `trial_started` row exists for the same `stripe_subscription_id` created within ±12 hours of `period_start`. Every path bails on lookup keys containing `credit` or `plato`, so AI credit and Plato money never enters the ledger. `manual`, `subscription_threshold` and other billing reasons create nothing.
- `StripeWebhookHandlerJob` is +23/−0 against production: two `CreateSubscriptionEventFromStripe.call` sites, each in its own `begin/rescue StandardError` that logs and swallows, in the main-plan branches of `customer.subscription.deleted` and `invoice.paid` (after `stripe_current_period_end_at`, `stripe_update_default_payment_method` and `organization_ai_credit_balance&.reset_ai_credits`).
- `CreateSubscriptionEvent` now takes `previous_plan` instead of `from_plan`/`to_plan`, derives `to_plan` from `organization.plan`, and fails when `previous_plan == organization.plan`. Duplicate window widened from 5 minutes to 24 hours, keyed on organization + `event_type` + `to_plan` + `stripe_subscription_id` (`from_plan` excluded). Both interactors gained a method-level `rescue StandardError` that re-fails with the generic message `'An error occurred while creating the SubscriptionEvent'`; since `Interactor::Failure < StandardError`, this also catches their own `fail!`, so the specific duplicate / "No plan change" messages never reach `result.message` (`log_assigned_free_plan_event` is the only caller that reads it).
- `Organization#subscription_started_trial_after_commit?` changed from `previous_status.nil? && current_status == 'trialing'` to `previous_status != 'trialing' && current_status == 'trialing'`. Because the enclosing callback returns unless `saved_changes.key?('stripe_subscription_status')`, the predicate is now effectively "the status just changed to `trialing`" — `canceled → trialing`, `active → trialing`, `past_due → trialing` all qualify. That branch runs `Notification::FreeTrialStartedJob`, `CreateSubscriptionEvent.call(event_type: 'trial_started')`, and `organization_ai_credit_balance&.reset_ai_credits`.
- No writer exists for `pending`, `downgraded_to_free` or `downgraded_plan`. Downgrades produce no row.

### Signup events

- `trackEvent("user_signed_up_client_side")` is removed from `AuthForm.tsx` and `SignupForm.tsx`, along with the now-unused `trackEvent` import in each. Signup tracking is server-side only. The event name was distinct from the server's `user_signed_up`, so nothing else changes.
- The generic `user_signed_up` is untouched and still fires at all three sites. A second, branched event is added beside each: `invited_user_signed_up` or `organization_owner_signed_up`, following the existing `invited_user_*` / `organization_owner_*` pairs in `OnboardingProfile.tsx` and `ProfileForm.tsx`.
- `registrations_controller.rb:53-54` branches on `@invite`, which is set at :33 only when `params[:invite_token]` resolved to a record — a token matching nothing leaves it nil and the user counts as an owner, consistent with `accept_invite(nil)` having done nothing for them. `registrations_controller.rb:211` is always an owner, since invite acceptance moved to the invites controller. `invites_controller.rb:81` is always an invited user.
- Both new events carry `'$set_once' => { originally_signed_up_as_owner: <bool> }`. `$set_once` rather than `$set` so the property records how someone first joined and cannot be rewritten. All four calls sit inside the existing `resource.active_for_authentication?` guards, so they fire with the generic event or not at all.

### Internal UTM tagging

`INTERNAL_UTM_PARAMS = "?utm_source=polymer_app&utm_medium=internal"` in `app/javascript/shared/lib/utils.js`, appended to 19 outbound URLs across 15 components (`UserNav.tsx`, `PolymerBar.tsx`, `FormLogoHeader.tsx`, `HeaderBar.tsx`, `AccountBilling.tsx`, `AccountCommentTemplates.tsx`, the five `AccountIntegrations*` files plus `AccountIntegrationsWebflow.tsx`, `AccountJobBoardCustomDomain.tsx`, `PurchaseAiCreditTopUpConfirmModal.tsx`, `UpdateAiCreditSubscriptionConfirmModal.tsx`). The constant hardcodes a leading `?`, so it is only safe on URLs with no existing query string; all current call sites qualify. `handleHelpClick` in `UserNav.tsx` and `PolymerBar.tsx` also gained a trailing slash (`https://help.polymer.co/`). Still untagged: `https://polymer.co/#pricing` in `UserNav.tsx`, `SubscriptionRequiredModalNew.tsx`, `SubscriptionRequiredModalNewLegacy.tsx`, `Login.tsx`, `AccountApiKeys.tsx`, and the job board footer (which keeps its own `?utm_source=polymerJobsPage`).

## Database

Schema version moves `2026_07_23_222213` → `2026_07_27_185856`; `db/data_schema.rb` moves `20260408040802` → `20260727185945`.

1. `20260724183710_add_attribution_identifier_columns_to_users.rb` — 8 nullable string columns on `users`: `ga_client_id`, `ga_session_id`, `fbclid`, `fbp`, `fbc`, `li_fat_id`, `google_click_id`, `adroll_first_party_cookie`.
2. `20260724183711_add_attribution_identifier_columns_to_organizations.rb` — 6 nullable string columns on `organizations` (`google_click_id` and `adroll_first_party_cookie` already existed there).
3. `20260727185856_add_stripe_subscription_id_and_amount_to_subscription_events.rb` — `stripe_subscription_id` (string), `amount` (integer cents), `billing_interval` (integer, `default: 0, null: false`), plus `change_column_default :subscription_events, :event_type, from: nil, to: 0`.

All new columns are nullable or defaulted, so these are metadata-only in PostgreSQL — no table rewrite. No index is added on any new column, including `subscription_events.stripe_subscription_id`, which both interactors' duplicate guards and the backfill's existence check filter on. An earlier commit in this branch (`89286fba8`) had a partial unique index on that column; the shipped migration does not.

4. Data migration `20260727185945_create_subscription_events_for_existing_paid_organizations.rb` — iterates `Organization.find_each`, skips orgs where `active_paid_plan?` is false and orgs that already have a `converted_to_paid`/`trial_converted_to_paid` row for their `stripe_subscription_id`, then calls `organization.stripe_subscription` (a live `Stripe::Subscription.retrieve` with `expand: ['items.data.price.tiers']`, one serial HTTP call per org, `Stripe::StripeError` rescued and logged per org) and skips `trialing` subscriptions. Writes one row per org: `trial_converted_to_paid` when `subscription.trial_end` is present else `converted_to_paid`, `from_plan: 'unknown'`, `to_plan: organization.plan`, `amount` = `price.unit_amount` (0 for `per_job` plans), `created_at` = `Time.at(subscription.billing_cycle_anchor)`, `billing_interval` left at `none`. Uses `create`, not `create!`. `down` raises `ActiveRecord::IrreversibleMigration`; backing it out means deleting `SubscriptionEvent.where(from_plan: 'unknown')` by hand. Re-running is safe (the existing-row guard skips).

`bin/heroku-release` runs `db:migrate` then `data:migrate`, so the backfill executes automatically in the release dyno.
