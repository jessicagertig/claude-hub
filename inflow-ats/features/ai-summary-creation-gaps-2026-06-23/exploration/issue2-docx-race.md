# Finding: issue2-docx-race

## TRACER FINDING

### issue
ISSUE 2: Chain Textract submission to DocxToPdfJob success (docx race). enqueue_new_job_application (job_application.rb:164-171) and the T2 controller update path (job_applications_controller.rb:107-116) both enqueue DocxToPdfJob and SubmitResumeToTextractJob as separate perform_later calls with no ordering. For a docx resume, SubmitResumeToTextract can run before DocxToPdfJob has attached resume_docx_to_pdf, so it sends the raw .docx S3 object to AWS Textract, which rejects it, and no usable TextractResult is produced.

### title
Docx resumes race: SubmitResumeToTextract can submit the raw .docx to AWS Textract before DocxToPdfJob attaches the converted PDF, producing no TextractResult

### is_real_gap

### current
enqueue_new_job_application (job_application.rb:164-171) enqueues NewJobApplicationJob (:165), DocxToPdfJob (:166), then a TEXTRACT_RESUME_PROCESSING-gated SubmitResumeToTextractJob (:167-169), all perform_later with no ordering. DocxToPdfJob#perform (docx_to_pdf_job.rb:6-8) calls handle_possible_docx_resume (job_application.rb:733-751), which returns unless resume_is_docx (:734), converts via convert_resume_docx_to_pdf (:736, ConvertApi at :753-759), attaches resume_docx_to_pdf (:740-744), and broadcasts JobChannel 'docx_to_pdf_conversion_complete' (:746); it does NOT enqueue SubmitResumeToTextractJob. SubmitResumeToTextract#submit_resume (submit_resume_to_textract.rb:8-41) selects resume_for_textract = has_resume_docx_to_pdf ? resume_docx_to_pdf : resume (:15) — has_resume_docx_to_pdf = resume_is_docx && resume_docx_to_pdf.attached? (job_application.rb:722-723) — and falls back to the RAW resume (the .docx) when conversion has not yet attached. It then calls parser.send_to_textract(hash_id, resume_for_textract) (:16), which calls Aws::Textract::Client#start_document_text_detection with s3_object.name = resume.key (textract_resume_parser.rb:20-42). Textract's StartDocumentTextDetection accepts only PDF/PNG/JPEG/TIFF; a .docx raises synchronously (Aws::Textract::Errors::UnsupportedDocumentException, a StandardError subclass, or InvalidS3ObjectException) BEFORE the TextractResult build at submit_resume_to_textract.rb:22. The rescues at :31 (InvalidS3ObjectException) and :36 (StandardError) both run @textract_result&.update_columns(...) (:33/:39) on a still-nil @textract_result, so the &. no-ops: NO TextractResult is created, the if @textract_result.save block (:24-30) never runs, so GetResumeTextFromTextractJob is never scheduled (:27). SubmitResumeToTextractJob#perform also rescues StandardError and only ap's (submit_resume_to_textract_job.rb:9-11) — no job retry. The SAME race exists on T2: job_applications_controller.rb:110-114 enqueues DocxToPdfJob (:112) then SubmitResumeToTextractJob (:114), both perform_later, no ordering.

### intended
For a docx resume, the Textract submission should be chained to fire only AFTER DocxToPdfJob has successfully attached resume_docx_to_pdf, so SubmitResumeToTextract always sends the converted PDF (never the raw .docx) to AWS Textract. For a PDF (non-docx) resume, Textract should still be triggered directly as today (no conversion step needed). Net: every resume that reaches Textract is a format Textract accepts, producing a valid TextractResult.

### delta
Today the docx Textract submission is NOT ordered after conversion: enqueue_new_job_application (:166-168) and the T2 controller (:112-114) fire DocxToPdfJob and SubmitResumeToTextractJob independently. When SubmitResumeToTextract wins the race for a docx, it sends the raw .docx to Textract (submit_resume_to_textract.rb:15-16 falls back to resume because resume_docx_to_pdf is not yet attached), Textract rejects the format, the exception fires before the TextractResult build (:22), and the rescue no-ops on a nil @textract_result (:33/:39). Result: zero TextractResult, no GetResumeTextFromTextractJob scheduled, no retry. The intended chaining (fire Textract from DocxToPdfJob success for docx; fire directly for PDF) does not exist anywhere in the code.

### later_resolved_check
PARTIALLY resolved by later actors, but not reliably. (1) The self-healing re-submit in get_resume_text_from_textract.rb:14-17 (re-enqueue SubmitResumeToTextractJob when textract_job_id is nil) does NOT help here: it only runs if a TextractResult already exists (parse_resume_text returns 'Resume has not been submitted to Textract' at :12 when none exists) AND if GetResumeTextFromTextractJob was scheduled — but in the docx-race failure no TextractResult is created (the build at :22 is never reached) and the poll job is never scheduled (:27 is inside the if @textract_result.save block). So self-healing never fires for this case. (2) The candidate is left resume-but-no-TextractResult. Later actors that re-submit and, by then, would find resume_docx_to_pdf attached (so they send the PDF and succeed): ValidateAiSummaryGeneration on a manual generate (validate_ai_summary_generation.rb:38-39, the unless @latest_textract_result branch), QueueBulkAiSummaryJobs backfill (queue_bulk_ai_summary_jobs.rb:28-30, pending_textract_ids = with_resume but not with_textract_results), and the rake backfill tasks (housekeeping_tasks.rake:409/445). These DO eventually produce a TextractResult once the PDF is attached — but only on a user-initiated manual/bulk generate or a manual rake run; there is no automatic timer/retry that re-submits a docx that lost the race on auto-creation. So for an org relying on auto-generation (should_auto_generate_ai_summaries?), a docx that loses the race silently never gets a summary until a human acts. This is a real resting state not advanced by any automatic later actor.

### solution_critique
Both proposed solutions are directionally correct and the analog (submit_resume_to_textract.rb:27 — a follow-on job enqueued from inside the current step's success path) is a GENUINE in-domain match for 'chain a follow-on after success.' Critique: (1) Solution #1 branches on resume_is_docx at every Textract-on-creation/upload site (model :167-169 and controller :113-114): PDF fires SubmitResumeToTextractJob directly; docx routes the enqueue into DocxToPdfJob. The flag re-check requirement at the new docx enqueue site is correctly noted (defense-in-depth, matching CLAUDE.md hard-rule pattern). Side-effect audit vs map is sound: status row (job_application.rb:170) is independent of Textract enqueue; the bridge selector and auto branch key off TextractResult/textract_processing summaries, not the enqueue site; PDF path is byte-identical. (2) Solution #2 correctly identifies the conversion-FAILURE regression: handle_possible_docx_resume rescues StandardError and only logs (job_application.rb:747-751), so if the Textract enqueue is placed at the broadcast line (:746) a docx whose conversion FAILS never fires Textract — strictly worse than today. The fix to place the enqueue in DocxToPdfJob#perform AFTER handle_possible_docx_resume returns (so it runs on both success and failure branches) is correct, BUT the tracer's note that DocxToPdfJob#perform itself rescues StandardError (docx_to_pdf_job.rb:12-15) means the enqueue must sit in an ensure or after a non-swallowing rescue — the tracer flagged this but did not specify the exact placement; the implementer must ensure the enqueue line is not skipped when handle_possible_docx_resume's internal failure propagates (it does not propagate — it is rescued inside handle_possible_docx_resume — so a plain post-call enqueue in perform suffices; only a raise from JobApplication.find at :7 would skip it, which is acceptable). One ADDITIONAL side effect the audit missed: moving the docx enqueue into DocxToPdfJob means the T9/manual-generate and bulk paths that ALSO enqueue both jobs are unaffected only if those paths do not separately rely on the model/controller enqueue — they use ValidateAiSummaryGeneration/QueueBulkAiSummaryJobs which enqueue SubmitResumeToTextractJob directly (:39/:55/:29) regardless of docx-ness, so a docx submitted via those paths STILL races unless they too branch. The proposed fix covers only the two creation/upload sites; the validate/bulk recovery sites would still submit a raw docx if conversion has not yet landed. This is acceptable for the stated scope (creation-side fix) but should be called out: the recovery actors remain race-exposed for docx, though in practice they run after conversion has usually completed. Net: solutions are viable; analog matches; the conversion-failure degenerate case is correctly handled; the residual docx race in the recovery actors is an unaddressed (but lower-severity, scoped-out) gap.
