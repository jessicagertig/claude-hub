# Finding: issue4-no-signal

## TRACER FINDING

### issue
Issue 4: No UI signal while a summary is in the awaiting_job_criteria or retrying window (or while AiJobCriteria is pending/in_progress). BROADCAST_STATUSES excludes both states, the status row stays initial_summary_pending, and the infinite list ignores per-status events.

### title

### current
BROADCAST_STATUSES = %w[pending textract_processing extracting summarizing scoring integrating succeeded failed] (ai_job_application_summary.rb:23) — omits awaiting_job_criteria and retrying. before_update :broadcast_status_change (ai_job_application_summary.rb:100-107) returns at :102 unless the status is in BROADCAST_STATUSES, so transitions INTO awaiting_job_criteria (orchestrate.rb:72 .update; score_job_application.rb:22,28,44 .update) and INTO retrying (score_job_application.rb:129 .update; integrate_analysis.rb:59 .update; generate.rb:175 update_columns which fires no callback at all) emit no JobChannel event. The AiJobApplicationSummaryStatus row enum has only none/initial_summary_pending/current/regenerating (ai_job_application_summary_status.rb:9-14) — there is NO distinct waiting/criteria state. set_initial_summary_pending (textract_result.rb:104-107) sets the row to initial_summary_pending and stamps ai_job_application_summary_id at pipeline start; update_summary_status_record (ai_job_application_summary.rb:69) advances the row to current only on status_succeeded?, so during awaiting_job_criteria/retrying the row stays initial_summary_pending with no score. What the FE sees in each window: (i) summary awaiting_job_criteria — the detail card (PlatoTab.tsx) reads fullSummaryStatus from useAiJobApplicationSummary (the full summary fetched by id; enabled because the row carries ai_job_application_summary_id), renders PlatoLoadingState for the awaiting_job_criteria branch (PlatoTab.tsx:163), but the full summary query ['aiJobApplicationSummary', id] is only invalidated by ai_summary_status_change (WebsocketJobChannelHandler.tsx:73-76), which never fires for this transition; the hook has no refetchInterval (useAiJobApplicationSummary.ts:42-46), so the card stays frozen at the LAST broadcast status (summarizing on the orchestrate.rb path that goes summarizing->awaiting_job_criteria without passing scoring) and shows PlatoLoadingState frozen at STATUS_TO_STEP.summarizing=1 ('Analyzing the candidate'); the list item shows nothing (JobApplicationNavItem.tsx:26-29 renders the Harvey ball only for current/regenerating with non-null score; row is initial_summary_pending); Activity shows nothing (JobApplicationActivity.tsx:80-83 gates on current/regenerating). (ii) AiJobCriteria pending/in_progress — same window as (i): the summary rests at awaiting_job_criteria while criteria runs; AiJobCriteria status writes (ai_job_criteria.rb / extract_criteria.rb) broadcast no JobChannel/GlobalChannel events at all, so no signal of criteria progress reaches the FE. (iii) summary retrying — same as (i) but the last broadcast status was scoring or integrating; card stays frozen on that loading step, list and Activity show nothing. GlobalChannel terminal events (AI_SUMMARY_COMPLETE generate_ai_job_application_summary_job.rb:74; AI_SUMMARY_FAILED textract_result.rb:153) fire only on terminal success/failure, never mid-window. The infinite list is refreshed only by terminal/completion events and explicitly ignores ai_summary_status_change (WebsocketJobChannelHandler.tsx:73-81; map 543,570).

### intended
While a summary is actively progressing through awaiting_job_criteria (waiting on AiJobCriteria), during the criteria pending/in_progress window, and during retrying, the user should see that something is happening — a live progress signal on at least the detail card (PlatoTab) and ideally a distinct list indicator — rather than a frozen loading state (or, on the list, nothing), so the absence of a result is legibly "in progress" rather than "stuck/done-with-nothing".

### delta
Two distinct sub-gaps, both proven: (A) NO BROADCAST on entry to awaiting_job_criteria and retrying — because both are excluded from BROADCAST_STATUSES (ai_job_application_summary.rb:23), the before_update broadcast (:102) is suppressed, so the detail card's full-summary query is never invalidated for these transitions and the card freezes at the prior broadcast status; the branch-committed spec ai_job_application_summary_spec.rb:57-62 explicitly asserts 'does not broadcast for awaiting_job_criteria / retrying', confirming this is current intended-by-spec behavior, NOT something the has_many criteria refactor closes. (B) NO ROW-LEVEL SIGNAL and LIST IGNORES per-status events — the status row stays initial_summary_pending (no distinct waiting state in the enum), JobApplicationNavItem renders no indicator for initial_summary_pending (JobApplicationNavItem.tsx:26-29), and the list query is never invalidated for ai_summary_status_change anyway (it only listens to terminal/completion events, WebsocketJobChannelHandler.tsx:77-81 + GlobalChannel). So this is genuinely BOTH 'no signal' (no broadcast fires for these statuses, sub-gap A) AND 'signal exists but list ignores it' (even broadcast statuses like summarizing/scoring don't refresh the list, sub-gap B). The card not going fully blank (it shows a frozen PlatoLoadingState) softens but does not close gap A.

### later_resolved_check
Partially resolved on the HAPPY path only. When AiJobCriteria reaches succeeded, resume_waiting_summaries (ai_job_criteria.rb:17,22-27, X3 fan-out) re-enqueues GenerateAiJobApplicationSummaryJob for each awaiting_job_criteria summary; the summary then advances awaiting_job_criteria -> scoring (.update score_job_application.rb:32) -> integrating -> succeeded, and scoring/integrating/succeeded ARE in BROADCAST_STATUSES, so the detail card refetches and unfreezes, and ai_summary_succeeded (ai_job_application_summary.rb:93-97) finally refreshes the list. So a LATER actor (X3) does eventually advance the frozen card — but ONLY once criteria succeeds. During the awaiting_job_criteria window itself there is no progress signal, and if criteria is stuck pending/failed (issue 6: a stuck-pending latest AiJobCriteria makes Job#extract_job_criteria/auto_extract_job_criteria return early at the existing_ai_job_criteria&.status_pending? guard, and a failed criteria does not fire resume_waiting_summaries — map 407), the awaiting_job_criteria window is UNBOUNDED and the frozen loading card never resolves. retrying is resolved by the summary's own retry advancing to a broadcast status; but the retrying-window itself emits no signal. Net: the resting state is advanced by X3 on success, so it is not a permanent gap on the happy path, but the in-window absence of any progress signal is real and, combined with issue 6, can become permanent.
