### issue

### title
AiJobApplicationSummaryStatus has no failed/error state and never clears denormalized columns; three windows leave the row stuck or stale (recoverable only by manual/bulk regen, except the auto-gen-ON S-D/T2 path)

### is_real_gap

### current
The enum AiJobApplicationSummaryStatus.status = {none:0, initial_summary_pending:1, current:2, regenerating:3} (ai_job_application_summary_status.rb:9-14) has NO failed/error value. Four writers exist (all writers grepped): (1) find_or_create_ai_job_application_summary_status.rb:15 update_columns(status:'regenerating') — STATUS-ONLY, does not touch score_percentage/headline/integrated_role_analysis/ai_job_application_summary_id; (2) find_or_create...:25-37 create-path build/save (else branch :33-34 sets only status='none'); (3) textract_result.rb:104-107 set_initial_summary_pending update_columns; (4) ai_job_application_summary.rb:74-80 success-path .update to 'current' (copies denormalized cols), guarded at :69 `return unless saved_change_to_status? && status_succeeded?`. WINDOW (a): when a summary ends failed (generate_ai_job_application_summary_job.rb:19,44 update_columns(status::failed); summary/generate.rb:180,184; score_job_application.rb:135,139; integrate_analysis.rb:64,68) or retrying (summary/generate.rb:175; score_job_application.rb:130; integrate_analysis.rb:59), the success-path writer's :69 guard is false so update_summary_status_record returns; the row stays at initial_summary_pending or regenerating — no writer moves it to a failed/error display state (none exists). WINDOW (b): regenerating is set status-only at find_or_create...:15, so old score_percentage/headline/integrated_role_analysis/ai_job_application_summary_id persist on the row while the new pipeline runs (or indefinitely if it never completes). WINDOW (c) S-D/T2 auto-continuation (auto-gen ON): textract_result.rb:68 does NOT early-return for a stale-succeeded summary (fails !stale?), find_or_create sets row to regenerating (:15), then Orchestrate selects the newest JobApplication-scoped summary with NO stale filter (orchestrate.rb:15) which is the stale-succeeded one, and the status_succeeded? branch returns without advancing (orchestrate.rb:46-48); no new summary reaches succeeded, so update_summary_status_record never fires; row remains regenerating with prior denormalized data; no credit charged (textract_result.rb:77 empty -> :82 returns before :84). With auto-gen OFF the row is not updated at all and stays current with stale data.

### intended
The status row should reflect the true display state of the latest summary: (a) when the latest summary ends failed (terminal), the row should expose a failed/error display state rather than appearing to be perpetually generating (initial_summary_pending) or perpetually regenerating; (b) while regenerating, the row should not present prior-review denormalized data as if it were a live result that risks persisting indefinitely if the new pipeline never completes; (c) the S-D/T2 resume-replacement auto-continuation should either advance the row to a fresh current result or not leave it parked at regenerating with the old data and no credit charged. Per pipeline CLAUDE.md issue 18, when disassociating/invalidating, ALL denormalized columns (score_percentage, headline, integrated_role_analysis, plus the FK) must be cleared together, not left stale.

### delta
PROVEN gaps: (a) No failed/error value in the AiJobApplicationSummaryStatus enum and no writer that transitions the row to such a state on a summary that ends failed; the row rests at initial_summary_pending/regenerating after a terminal failure. (b) The regenerating transition (find_or_create...:15) is status-only and never clears the stale denormalized columns, violating the "clear ALL denormalized columns" rule (pipeline CLAUDE.md issue 18) for the duration of the regeneration window (and forever on window c). (c) On the auto-gen-ON S-D/T2 path, no later actor advances the row: Orchestrate's stale-blind newest-summary selection (orchestrate.rb:15) lands on the stale-succeeded summary and returns (orchestrate.rb:46-48), so update_summary_status_record never fires.

### solution_critique
Solution 1 (add failed/error enum value + writer in update_summary_status_record extending the :69 guard to handle status_failed?): the analog (success-path writer ai_job_application_summary.rb:74-80) is a CORRECT structural match for the .update-based failure writers — same status row, same column set. BUT it has a fatal coverage hole the tracer's side-effect audit MISSED: update_summary_status_record is an after_commit callback that ONLY fires when the summary is changed via .update/.save, NOT via update_columns. The two most common terminal-failure writers (generate.rb:175/180/184 and generate_ai_job_application_summary_job.rb:19/44 — the retries-exhausted and StandardError paths, which are the PRIMARY way a summary ends failed) all use update_columns and will NEVER trigger the proposed callback writer. So solution 1 as written would fix only the score_job_application/integrate_analysis JSON-parse/StandardError sub-branches (.update) and silently miss the dominant failure paths. The spec MUST either (i) convert those update_columns failure writes to .update, or (ii) add the status-row failed write directly at each failure site / in a shared helper, not rely on the after_commit callback. This is a structural-match failure: the analog fires on success which always goes through .update (generate.rb final success uses .update — verify), but failure does not uniformly go through .update. Solution 1's counter_culture analysis is correct (a failed value outside status IN 2,3 decrements ai_job_application_summaries_count — a product decision). Solution 2 (clear denormalized cols on the regenerating transition): structurally sound, update_columns keeps status=3 in-range so counter unaffected — correct. Correctly flagged as a deliberate behavior change conflicting with existing spec expectations (the create-path :27-32 and the success path intentionally show prior data); needs user approval. Solution 3 (fix S-D/T2 dead end by building a fresh summary / stale-filtering Orchestrate): correctly identified as highest-blast-radius and a billing change (would newly charge a credit on auto-regen); correctly recommended as a separate spec cycle per pipeline CLAUDE.md rule 10. Note: solution 3 alone does not need the enum change; solutions 1, 2, 3 address orthogonal slices and should be scoped independently. Overall the tracer's solutions are directionally right but solution 1's side-effect audit is incomplete on the update_columns-vs-callback issue, which is the single most important correction.
