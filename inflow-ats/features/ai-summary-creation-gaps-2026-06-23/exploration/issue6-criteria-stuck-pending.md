# Finding: issue6-criteria-stuck-pending

## TRACER FINDING

### issue
Issue 6: Can an AiJobCriteria record sit in `pending` forever with no actor advancing it? (The incident's criteria record never left pending.)

### title
AiJobCriteria stuck-pending-forever is REAL: a pending criteria record has exactly one advancing actor (its own ExtractJobCriteriaJob), and once a job's latest_ai_job_criteria is pending, every other entry point (extract_job_criteria, auto_extract_job_criteria, Orchestrate, ScoreJobApplication) is guarded to NOT create or re-drive it — so if that single job is lost/never-runs/returns-early, nothing recovers it

### is_real_gap
True

### gap_confidence
proven

### current
A criteria record is created `pending` in exactly two live places, both `ai_job_criteria.new(status: :pending)` then `save` then `ExtractJobCriteriaJob.perform_later(new_ai_job_criteria.id)`: `auto_extract_job_criteria` (app/models/job.rb:696-711, enqueues with wait:30s if a prior record exists, else immediately) and `extract_job_criteria` (app/models/job.rb:713-723). The ONLY actor that advances a given pending record to in_progress is that record's own `ExtractJobCriteriaJob` -> `ExtractCriteria#extract`, whose first status write is `@ai_job_criteria.update_columns(status: :in_progress)` at app/services/ai_job_application_action/scoring/extract_criteria.rb:28. ExtractJobCriteriaJob#perform (app/jobs/extract_job_criteria_job.rb:12-29) does `find_by(id:)` then `return unless ai_job_criteria` (:13-14); ExtractCriteria#extract does `return unless @ai_job_criteria` (:20), `return unless @job` (:23), `return unless @organization` (:26) BEFORE the :28 in_progress write. All non-pending status writers (in_progress :28; succeeded :140 via .update which fires resume_waiting_summaries; retrying :146 + re-raise; failed :32/:62/:122/:151/:155 and extract_job_criteria_job.rb:9/:28) only execute once perform/extract actually runs. Crucially, three guards reference status_pending? and make pending self-protecting: extract_job_criteria `return if existing_ai_job_criteria&.status_pending?` (job.rb:718), auto_extract_job_criteria same (job.rb:701), and Orchestrate check_criteria_and_score `extract_job_criteria unless ai_job_criteria&.status_pending? || ...status_in_progress?` (orchestrate.rb:80). ScoreJobApplication#score, when criteria is pending/in_progress/retrying, sets the summary to awaiting_job_criteria and returns WITHOUT calling extract_job_criteria (score_job_application.rb:27-30). So no actor creates a fresh criteria record while the latest is pending, and no actor re-enqueues ExtractJobCriteriaJob for an existing pending record. There is NO scheduler/cron (config/sidekiq.yml has no cron block, no sidekiq-cron gem in Gemfile.lock) and NO rake task that re-drives pending criteria (lib/tasks/recurring_tasks.rake re-drives only Textract resumes, not criteria; lib/tasks/ai_bulk_extract.rake does summary structured-data only). The only re-driving actor that exists for criteria is `retry_on CustomErrorAiSummary attempts:3` on ExtractJobCriteriaJob (extract_job_criteria_job.rb:5), but that path goes pending->in_progress->retrying->retry, never resting at pending.

### intended
A criteria record created pending should reliably reach a terminal state (succeeded or failed) so that (a) awaiting_job_criteria summaries depending on it get resumed via resume_waiting_summaries on succeeded (ai_job_criteria.rb:21-29), and (b) the job's latest_ai_job_criteria is not permanently stuck pending, which would block all future criteria extraction for that job (the pending-guard poison). The encoded intended behavior (uncommitted specs) confirms the design DELIBERATELY rests at pending/in_progress without re-triggering: orchestrate_spec.rb:444-450 asserts that when criteria is in_progress, Orchestrate does NOT re-trigger extract_job_criteria and does NOT score. The design therefore relies entirely on the single ExtractJobCriteriaJob completing; there is no intended fallback/sweeper for a lost or early-returning job.

### delta
A criteria record CAN sit in pending forever. Once a job's latest_ai_job_criteria is pending, every creating/re-driving entry point is guarded off (job.rb:701, job.rb:718, orchestrate.rb:80, and ScoreJobApplication never calls extract for pending). The single advancing actor is the record's own ExtractJobCriteriaJob. If that job (1) is never enqueued because new_ai_job_criteria.save returns false (job.rb:704/721 early return leaves NO pending record at all — not the stuck case) — note this branch does NOT leave a stuck pending record because nothing was saved; the stuck case requires the record to be saved pending AND the job to not advance it; (2) is enqueued but never runs (Sidekiq drop, queue backlog at deploy, process kill before the job pops, or the job exhausting Sidekiq's own :max_retries:3 in sidekiq.yml for a non-CustomErrorAiSummary failure that somehow escapes the rescue — though all StandardErrors are rescued at extract_job_criteria_job.rb:23-28 and write failed, so realistic loss is enqueue-never-runs, not in-perform); or (3) runs but returns before the :28 in_progress write (record deleted between enqueue and run -> :14/:20 return; or @job nil -> :23 return; or @organization nil -> :26 return — the latter two are edge cases since belongs_to :job is required and Job belongs_to :organization counter_cache is required) — then the record is permanently pending and nothing recovers it. The DOMINANT, production-realistic precondition is #2: ExtractJobCriteriaJob enqueued but never executed (infra: lost job / backlog / deploy kill). The poison-guard then prevents any later actor from creating a replacement criteria record for that job, so ALL future job_applications on that job rest at awaiting_job_criteria indefinitely (this is the amplifier connecting issues 4 and 5).

### later_resolved_check
Explicitly checked every potential later actor. (a) resume_waiting_summaries only fires on succeeded (ai_job_criteria.rb:22) — never reached, so it does NOT resolve a pending record. (b) retry_on CustomErrorAiSummary (extract_job_criteria_job.rb:5) only re-drives a record that already entered perform and raised — it does not re-enqueue a job that was lost before running, and it does not create a fresh record. (c) Orchestrate check_criteria_and_score (orchestrate.rb:80) explicitly does NOT call extract_job_criteria when criteria is pending — confirmed by orchestrate_spec.rb:444-450 — so a later summary's Orchestrate pass does NOT resolve it. (d) ScoreJobApplication (score_job_application.rb:27-30) sets summary awaiting and returns, no extract call, for pending criteria — does NOT resolve it. (e) extract_job_criteria / auto_extract_job_criteria both `return if existing_ai_job_criteria&.status_pending?` (job.rb:718/701) — a publish (handle_status_changed_to_published -> auto_extract_job_criteria, job.rb:560) or a description change (handle_description_change -> auto_extract_job_criteria, job.rb:480/731) does NOT create a replacement and does NOT resolve it. (f) No scheduler/cron/rake re-drives pending criteria. Conclusion: NO later actor resolves a stuck-pending criteria record. The resting state is terminal-by-omission, which makes it a genuine gap, not a resting-state-that-a-later-actor-advances.

### final_delta
An AiJobCriteria record CAN sit in `pending` permanently. A pending record has exactly ONE advancing actor — its own ExtractJobCriteriaJob → ExtractCriteria#extract, whose first status write is `update_columns(status: :in_progress)` (extract_criteria.rb:28). Once a job's latest_ai_job_criteria is pending, ALL other entry points are guarded off: auto_extract_job_criteria (job.rb:701), extract_job_criteria (job.rb:718), Orchestrate#check_criteria_and_score (orchestrate.rb:80), and ScoreJobApplication for the pending branch (score_job_application.rb:27-30, no extract call). No cron, no sidekiq-cron gem, no rake sweeper re-drives pending criteria. retry_on only re-drives a record that already entered perform and raised (path: in_progress→retrying→retry, never resting at pending). Therefore if the single ExtractJobCriteriaJob never advances the record, NOTHING recovers it, and the pending poison-guard blocks creation of any replacement criteria record for that job — so every subsequent job_application on that job rests at awaiting_job_criteria indefinitely (amplifier connecting issues 4 and 5). LOSS VECTORS (refined, strongest first): (V1 — code-traceable, the tracer UNDER-credited this) ENQUEUE-INSIDE-TRANSACTION RACE on the auto_extract_job_criteria path: handle_before_update is a before_update callback (job.rb:60), so handle_status_changed_to_published→auto_extract_job_criteria (job.rb:560) and handle_description_change→auto_extract_job_criteria (job.rb:731) execute new_ai_job_criteria.save AND ExtractJobCriteriaJob.perform_later (job.rb:703-709) INSIDE the Job's update transaction. Rails 6.1.7.7 (Gemfile.lock:406) has NO enqueue_after_transaction_commit (added in Rails 7.2; not configured anywhere). A Sidekiq worker can pop the job before the parent transaction commits → find_by(id:) returns nil → `return unless ai_job_criteria` (extract_job_criteria_job.rb:14) → job exits silently; the criteria record then commits pending with no re-drive. This is the path that creates the FIRST criteria record on publish, where stuck-pending poisons every later applicant. (V2 — infra, the tracer's stated dominant) job enqueued but never executed (Sidekiq job loss on deploy/crash, backlog eviction). (V3 — edge) record deleted between enqueue and run, or @job/@organization nil before extract_criteria.rb:28 (edge cases given belongs_to required). All three leave the record permanently pending. The DELTA holds and is in fact UNDERSTATED by the tracer, which did not identify V1.

### solution_critique
The tracer correctly defers BUILDING (investigate != build) and identifies the right shape for a future fix. Critique of the two scoped conditions: (A) sweeper/reaper for stuck-pending records re-enqueuing ExtractJobCriteriaJob for the EXISTING record id (not a new record, to dodge the poison guard) — analog-sound. (B) make early-return guards at extract_criteria.rb:23/26 write :failed instead of returning silently — reasonable hardening but does NOT address the dominant V1/V2 vectors (those never reach extract_criteria at all; the job returns at extract_job_criteria_job.rb:14 or never runs). This is the minimal, targeted fix for the most code-attributable vector and would prevent most stuck-pending records at the source, making a sweeper a defense-in-depth backstop rather than the only mitigation. ### refutations
- Considered: does Sidekiq's :max_retries:3 (sidekiq.yml) recover a lost job? No — :max_retries applies to jobs that RAISE. A job that returns silently at extract_job_criteria_job.rb:14 (record not found) does NOT raise, so Sidekiq marks it succeeded; no retry. Refutation fails; gap stands.
- Considered: does the StandardError rescue (extract_job_criteria_job.rb:23-28) writing :failed mean every in-perform failure terminates? Yes for in-perform failures — but the stuck-pending case is precisely the case where perform never reaches the rescue (returns at line 14, or job never pops). Refutation fails; gap stands.
- Considered: is the in-transaction enqueue actually safe because Sidekiq client buffers within the DB transaction? No — Sidekiq pushes to Redis immediately on perform_later; Redis is not part of the Postgres transaction. A fast worker can pop before Postgres commits. Refutation fails; this is the documented Rails<7.2 footgun. Strengthens the gap.
- Considered: could the after_commit on AiJobCriteria (resume_waiting_summaries) or any Job after_commit re-drive? No — Job has after_commit complete_setup_workers (on:create) and handle_after_update_commit (on:update); neither touches criteria. AiJobCriteria after_commit only resumes on succeeded. Refutation fails.

### missed_paths
- V1 ENQUEUE-INSIDE-TRANSACTION RACE: auto_extract_job_criteria runs inside the Job before_update transaction (job.rb:60 before_update :handle_before_update -> handle_status_change -> handle_status_changed_to_published (job.rb:560) and handle_description_change (job.rb:731) -> auto_extract_job_criteria). new_ai_job_criteria.save (job.rb:704) and ExtractJobCriteriaJob.perform_later (job.rb:707/709) both run pre-commit. Rails 6.1 has no enqueue_after_transaction_commit, so a worker can run the job before commit, hit `return unless ai_job_criteria` (extract_job_criteria_job.rb:14), and leave the record stuck pending after commit. The tracer listed only generic infra loss and record-deletion, not this code-structural race. This is the most production-realistic vector because it occurs on the publish path that creates the first criteria record.
- Scope note the tracer got right but worth restating: score_job_application.rb:21-25 (blank/failed criteria) and :42-47 (empty criteria array) DO call @job.extract_job_criteria — but neither applies to a pending record, so they do not constitute a recovery path for the stuck-pending case. No miss here; verified.
- Asymmetry the tracer did not call out: the in-transaction race (V1) applies ONLY to the auto_extract_job_criteria callers (publish/description-change). The extract_job_criteria callers via orchestrate.rb:80 and score_job_application.rb:23/45 run inside Sidekiq jobs OUTSIDE the Job update transaction, so those enqueues are not subject to the race. This matters for a fix: the race fix (enqueue after commit) targets the model-callback path specifically.
