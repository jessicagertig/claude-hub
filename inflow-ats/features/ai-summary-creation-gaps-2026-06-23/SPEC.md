## Summary

The AI-summary/criteria pipeline has six creation/visibility gaps. The two concrete asks: (1) auto-generate never actually creates an `AiJobApplicationSummary` — auto-gen applications get no summary until a human manually generates; and (2) for `.docx` resumes, Textract is submitted the raw `.docx` before the converted PDF is attached, so the docx path produces no usable `TextractResult` and the pipeline never starts. Beyond those: the `AiJobApplicationSummaryStatus` row has no failed state (a failed summary leaves the UI showing "generating" or stale data); the `awaiting_job_criteria`/`retrying` windows emit no UI signal (the detail card freezes); and the reported "criteria stuck pending" incident is caused by criteria extraction being enqueued **inside the Job update transaction** (a Sidekiq worker can run the job before the row commits, leaving it `pending` forever) — NOT by the `has_one`→`has_many` change (which is sound but orthogonal).

## Stack scope

Backend (Rails) for all six; Frontend (React/TS) for W4 and W5 only. No new tables. One Rails enum gains a value (W5; integer column already exists — no migration). **Never stage/commit `db/schema.rb`.**

## Workstreams (ordered by priority)

Implement in this order. W1–W3 + W6 are backend, high-confidence, and resolve the named asks + the incident; W4–W5 add visibility.

### W3 — Enqueue criteria extraction AFTER the Job transaction commits  (Issue 5 root cause / V1; resolves the incident)

**Behavior:** `ExtractJobCriteriaJob` must be enqueued only after the Job's update has committed, so a Sidekiq worker never finds a not-yet-committed `AiJobCriteria` (which leaves it `pending` forever).

**Root cause (proven, reproduced):** `before_update :handle_before_update` (`job.rb:60`) → `handle_status_changed_to_published` (`job.rb:544-560`) and `handle_description_change` (`job.rb:726-731`) → `auto_extract_job_criteria` (`job.rb:696-711`), which does `new_ai_job_criteria.save` + `ExtractJobCriteriaJob.perform_later` (`:704-709`) **inside the before_update transaction**. Rails 6.1.7.7 has no `enqueue_after_transaction_commit`, so the job can run before commit → `AiJobCriteria.find_by(id:)` nil → `extract_job_criteria_job.rb:14` `return unless ai_job_criteria` → silent exit → criteria stuck `pending`; the `pending`-guard (`job.rb:701/718`) then blocks all future extraction (incl. a manual generate). This is the incident; `has_many` does not address it.

**Change:** move ONLY the criteria-extraction trigger call off the `before_update` chain so it runs after the Job commits. Today `handle_status_changed_to_published` (`:560`) and `handle_description_change` (`:731`) call `auto_extract_job_criteria` synchronously in `before_update`. Relocate **only those two `auto_extract_job_criteria` calls** — the rest of `handle_status_changed_to_published` (`touch(:published_at)` `:546`, `update_column(:originally_published_at,...)` `:549`, the five `perform_later`s `:551-558`) and the description-change guards STAY in the before_update chain.

**PRIMARY — option (b), `previous_changes` in after_commit (analog-matching):** detect the publish/description-change condition in the after_commit using `previous_changes` — the SAME mechanism `handle_after_update_commit` already uses to enqueue Webflow/WhatJobs jobs (`:501/:507/:537-538`); this keeps W3 structurally consistent with the analog (pipeline #14 — follow the analogous `after_commit` pattern). **`previous_changes` has STRING keys (NOT symbols)** — the analog confirms this by doing `previous_changes.keys.map(&:to_sym)` at `:497/:501/:507`. So use `previous_changes['status']` / `previous_changes['description']` (string keys), or equivalently the Rails 5.1+ dirty API `saved_change_to_status?` / `saved_change_to_description?` + `saved_change_to_description` (which returns `[old, new]` and fires correctly in after_commit). Do NOT use symbol keys (`previous_changes[:description]` returns `nil` — `previous_changes` is a plain string-keyed Hash, not HashWithIndifferentAccess). **Mandatory rewrite under option (b):** `description_meaningfully_changed?` (`:734-737`) reads `description_was` (`:735`), which in an `after_commit` returns the CURRENT value (dirty tracking is RESET), so it would compare `description` to itself and always be false → criteria extraction would NEVER fire on a description change. The after_commit check MUST instead apply the same sanitize-and-compare to the OLD value `previous_changes['description']&.first` (or `saved_change_to_description&.first`) vs the NEW value `&.last`, and detect publish via `previous_changes.key?('status') && published?` (or `saved_change_to_status? && published?`).

**FALLBACK — option (a), instance flag captured in before_update:** if the plan judges the option-(b) `previous_changes['description']` rewrite too error-prone, capture the publish/description-change DECISION during `handle_before_update` (where dirty state is live: `status_changed? && published?`; `description_changed? && published? && description_meaningfully_changed?`) onto an instance flag (e.g. `@should_extract_criteria_after_commit`), then call `auto_extract_job_criteria` from after_commit if set. NOTE: option (a) introduces an instance-flag mechanism the analog does NOT use — acceptable only as a fallback, and it still must satisfy the `skip_update_callback` requirement below.

**`skip_update_callback` (HARD requirement):** today criteria extraction fires in `before_update` REGARDLESS of `skip_update_callback` — `handle_before_update` (`:476-485`) runs `handle_status_change`/`handle_description_change` with no such guard. `handle_after_update_commit` returns early on `return if skip_update_callback` (`:492`), and the flag is set `true` by `Settingsable` (`settingsable.rb:22,40,51`). To preserve current behavior, the after_commit criteria extraction MUST run **irrespective of `skip_update_callback`** — place it BEFORE the `:492` guard, or in a DEDICATED separate `after_commit on: [:update]` callback not subject to that guard. Do NOT let it inherit the `skip_update_callback` early-return.

The plan uses option (b) (analog-matching) unless the rewrite is judged too error-prone, in which case option (a); both are subject to the description-rewrite trap and the `skip_update_callback` requirement above. The `AiJobCriteria.new(...).save` and the `ExtractJobCriteriaJob.perform_later` then both happen post-commit (the record's own save opens its own transaction and commits before the enqueue), so the worker always finds the row.

**Asymmetry note:** the `extract_job_criteria` callers via `orchestrate.rb:80` and `score_job_application.rb:23/45` already run inside Sidekiq jobs OUTSIDE the Job-update transaction, so they are NOT subject to V1 — this fix targets only the model-callback (publish / description-change) path.

**Constraint:** preserve the existing behavior of `auto_extract_job_criteria` (the `should_auto_generate`/flipper guard at `job.rb:697`, the `wait: 30.seconds` debounce at `:706-710`, the pending-guard). Only the WHEN (after commit) changes, not the WHAT.

**Out of scope (deferred, per KICKOFF issue 6):** a sweeper/reaper for already-stuck `pending` records and residual infra loss (V2/V3), and making `extract_criteria.rb:23/26` early-returns write `failed`. Documented in `FINDINGS.md`; needs usage data.

**Tests:** `spec/models/job_criteria_lifecycle_spec.rb` (the criteria-lifecycle home; `spec/models/job_spec.rb` does NOT exist) — publishing a job enqueues `ExtractJobCriteriaJob` (and creates the `AiJobCriteria`). **The enqueue-happens-after-commit assertion must be DETERMINISTIC, not a ghost test:** a bare `expect(ExtractJobCriteriaJob).to have_been_enqueued` passes for BOTH the buggy before_update and the fixed after_commit code (the test adapter enqueues regardless of transaction, and a single-threaded transactional test has no real race). Instead, spy on the enqueue and assert `previous_changes` is populated at call time — e.g. capture in `allow(ExtractJobCriteriaJob).to receive(:perform_later) { ... }` that `job_record.previous_changes` includes `'status'` (publish) / `'description'` (description-change). In before_update `previous_changes` is EMPTY (the delta is in `changes`) → the assertion FAILS (proves the bug); in after_commit it holds `['draft','published']` → PASSES. Document that the actual concurrency race is not unit-testable single-threaded; the after-commit timing is additionally verified by the structural placement in `handle_after_update_commit` (code review). Add a regression asserting the publish path creates exactly one criteria and enqueues its job. Confirm `has_many` semantics: extraction after a failed criteria creates a NEW record (no overwrite); poison-guard behavior is unchanged. (These add the multi-row has_many coverage the 5 pre-loaded specs lack.)
