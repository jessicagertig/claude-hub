Assessed the spec's test plan against actual failure modes, ghost-test risk, stub correctness (#7), and pipeline #19 (eager companion record). Verified all named test homes EXIST (see source-accuracy angle) and confirmed the test infrastructure (`spec/support/ai_credits_test_helpers.rb`: `create_credit_test_organization/_job/_job_application/_summary`; `use_transactional_fixtures = true` with after_commit firing -- confirmed by existing `textract_result_ai_trigger_spec.rb` which tests the `queue_ai_summary_job` after_commit).

## Findings

- **F1 [MED]** -- W3's "enqueue happens after commit" test, as specified, is a GHOST TEST that cannot distinguish the fix from the bug. SPEC.md W3 test (line 80) says "the enqueue happens after commit (e.g., assert via `after_commit` semantics / that the record is persisted/committed when the job would run)." But `expect(ExtractJobCriteriaJob).to have_been_enqueued` after publishing PASSES for BOTH before_update (buggy) and after_commit (fixed) code -- the test queue adapter enqueues regardless of transaction, and in a single-threaded transactional test there is no real race, so "record findable at enqueue" is also true for the buggy code. Per hub "Ghost tests are blockers." Fix: the spec must require a test that DETERMINISTICALLY distinguishes the timing -- spy on the enqueue and assert `previous_changes` is populated at call time: e.g. `allow(ExtractJobCriteriaJob).to receive(:perform_later) { |*| expect(job_record.reload.previous_changes).to include('status') }` (or capture `previous_changes` in the spy and assert outside). In before_update, `previous_changes` is EMPTY (the change is in `changes`, not yet committed) -> the assertion FAILS -> proves the bug; in after_commit, `previous_changes` holds `['draft','published']` -> PASSES. This is the only deterministic proxy for the race in a unit test. Also: document that the actual concurrency race is not unit-testable single-threaded; the timing is additionally verified by the structural placement in `handle_after_update_commit` (code review). APPLIED.

- **F2 [MED]** -- W5 test plan must cover EACH terminal-failure SITE -> row `failed`, not just "the new method". SPEC.md W5 test (line 132) says "a terminal-failed summary (via each failure site / the new method)". To avoid ghost coverage (testing only `record_failure` in isolation while the SITES still bypass it), the spec must require: (a) a direct `record_failure` unit test (summary->failed via update_columns, row->failed via .update with cleared denormalized cols + counter decrement); AND (b) at least one integration test per MECHANISM CLASS proving the SITE routes through it -- one `update_columns` site (`generate.rb:180` or `generate_ai_job_application_summary_job.rb:19`), one `.update` site (`score_job_application.rb:134` or `integrate_analysis.rb:64`), and the C8 `destroy`->`record_failure` site (`get_resume_text_from_textract_job.rb:19`). Each asserts the status row reaches `failed` with cleared cols and `jobs.ai_job_application_summaries_count` decremented (when the row was current/regenerating). APPLIED.

- **F3 [LOW]** -- W1 C7 test should assert the "earlier failed TextractResult present" case (already added to the C7 side-effect note in the lifecycle angle). The test plan (line 43) should cross-reference it so the impl writes it. APPLIED (folded into the C7 amendment from the lifecycle angle; added a pointer in the W1 tests line).
