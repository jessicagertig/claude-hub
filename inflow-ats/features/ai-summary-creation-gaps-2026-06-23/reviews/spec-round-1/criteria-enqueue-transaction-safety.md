# criteria-enqueue transaction safety (W3) — Round 1

Verified the V1 race claim against live callback ordering, and whether moving the criteria enqueue from `before_update` to `after_commit` preserves the publish/description-change trigger CONDITIONS and the guards/debounce exactly.

Chain: `job.rb:20,58,60,476-485,491-511,513-535,544-561,696-711,713-723,726-738` -> `extract_job_criteria_job.rb:13-14` -> `app/models/concerns/settingsable.rb:22,40,51`.

## V1 race — CONFIRMED
`before_update :handle_before_update` (`:60`) -> `handle_before_update` (`:476-485`, `if changed?` -> `handle_status_change` `:479` + `handle_description_change` `:480`) -> `handle_status_changed_to_published` (`:560`) / `handle_description_change` (`:731`) -> `auto_extract_job_criteria` (`:696-711`): `new_ai_job_criteria.save` (`:704`) runs inside the OUTER Job-update transaction (nested save = same transaction, does NOT independently commit), then `ExtractJobCriteriaJob.perform_later(new_ai_job_criteria.id)` (`:707/:709`) enqueues a job referencing an UNCOMMITTED id. On Rails 6.1.7.7 (no `enqueue_after_transaction_commit`) the worker can run before commit -> `AiJobCriteria.find_by(id:)` nil (`extract_job_criteria_job.rb:14`) -> silent exit -> stuck `pending`. The after_commit fix is correct in principle: in after_commit the Job txn has closed, so `new_ai_job_criteria.save` opens its own txn and commits before the enqueue. CONFIRMED.

## Findings

- **F1 [HIGH]** -- Naively moving the criteria call into `handle_after_update_commit` BREAKS description-change detection (dirty-tracking is reset post-commit). The publish/description triggers currently evaluate live dirty state in `before_update`: `handle_description_change` (`:726-732`) uses `description_changed?` (`:727`) and `description_meaningfully_changed?` (`:734-737`), and the latter reads **`description_was`** (`:735`). In an `after_commit` callback, dirty tracking is reset -- `description_changed?` is false and `description_was` returns the CURRENT value -> `description_meaningfully_changed?` compares `description` to itself -> always false -> criteria extraction NEVER fires on a description change. SPEC.md W3 (line 72) offers option (b) "detect the publish/description-change condition in `handle_after_update_commit` via `previous_changes`" but does not warn that `description_meaningfully_changed?`/`description_was` must be rewritten to use `previous_changes[:description]` (which holds `[old, new]` post-commit). Fix: the spec must (i) PREFER option (a) -- capture the publish/description-change DECISION in `before_update` (where `status_changed?`/`description_changed?`/`description_was` are live) into an instance flag, then call `auto_extract_job_criteria` from after_commit based on the flag; and (ii) if option (b) is taken instead, explicitly require rewriting the description-meaningful-change check to use `previous_changes[:description]&.first`/`&.last` rather than `description_was`. APPLIED.

- **F2 [HIGH]** -- Moving the criteria call into `handle_after_update_commit` after its `return if skip_update_callback` guard (`:492`) silently subjects criteria extraction to `skip_update_callback` for the FIRST time -- a behavior change. Today criteria extraction fires in `before_update` REGARDLESS of `skip_update_callback`: `handle_before_update` (`:476-485`) runs `handle_status_change`/`handle_description_change` inside `if changed?` (`:478`) with NO `skip_update_callback` check (only `UpdateDistributionsJob` `:481` is guarded by it). `skip_update_callback` is set `true` by the `Settingsable` concern (`settingsable.rb:22,40,51`) on Job settings updates. `handle_after_update_commit` returns early on it (`:492`). If a publish or meaningful description change co-occurs with a settings update (or any flow that sets the flag), criteria extraction that fires today would NOT fire after the move. Fix: the spec must require the criteria extraction in after_commit to run irrespective of `skip_update_callback` -- either placed BEFORE the `return if skip_update_callback` at `:492`, or in a dedicated separate `after_commit` callback not subject to that guard. APPLIED.

- **F3 [MED]** -- The spec must be explicit that ONLY the criteria enqueue moves, not the rest of `handle_status_changed_to_published`. `handle_status_changed_to_published` (`:544-561`) also does `touch(:published_at)` (`:546`), `update_column(:originally_published_at, ...)` (`:549`), and 5 `perform_later`s (`:551-558`). These must STAY in the before_update chain; only the `auto_extract_job_criteria` call (`:560`) relocates. Likewise `handle_description_change` (`:726-732`) only relocates its `auto_extract_job_criteria` call (`:731`); the guard conditions stay where dirty state is live (or are captured per F1). SPEC.md W3 (line 72) says "move the criteria-extraction trigger off the `before_update` chain" -- correct intent but should name the single call so an impl agent does not relocate `touch`/`update_column`/other jobs. APPLIED.

## Verified-correct (no change)
- Debounce + guards preserved IF `auto_extract_job_criteria` is CALLED (option a) rather than reimplemented: the method self-contains the Flipper guard (`:697`), pending poison-guard (`:701`), and the `existing_ai_job_criteria` -> `wait: 30.seconds` debounce branch (`:706-710`); none depend on dirty tracking. SPEC.md line 76 ("preserve... Only the WHEN changes") is satisfied by option (a). If option (b) reimplements the trigger, the debounce branch must be preserved (it lives inside `auto_extract_job_criteria`, so calling the method is safest). CONFIRMED.
- No re-entrancy/loop: `auto_extract_job_criteria` builds+saves a NEW `AiJobCriteria` (a different model) and does not update the Job, so calling it from a Job `after_commit on: [:update]` does not re-fire the Job after_commit. CONFIRMED.
- Asymmetry note correct: `orchestrate.rb:80` (`job.extract_job_criteria`) and `score_job_application.rb:23,45` (`@job.extract_job_criteria`) run inside Sidekiq jobs OUTSIDE the Job-update transaction, so they are not subject to V1 and must NOT be altered. CONFIRMED (SPEC.md line 74).
- Sweeper/reaper for already-stuck `pending` correctly DEFERRED (SPEC.md line 78; approved baseline -- do not re-litigate).

## Amendments Applied
- SPEC.md W3 (line 72): PREFER option (a) (capture publish/description-change decision in before_update into an instance flag, call `auto_extract_job_criteria` from after_commit); warn that option (b) must rewrite `description_meaningfully_changed?`/`description_was` to use `previous_changes[:description]`.
- SPEC.md W3 (line 72): require the after_commit criteria extraction to fire irrespective of `skip_update_callback` (place before the `:492` guard or in a dedicated after_commit callback), matching today's before_update behavior.
- SPEC.md W3 (line 72): name the single relocating call (`auto_extract_job_criteria` at `:560`/`:731`); the rest of `handle_status_changed_to_published` (`touch`/`update_column`/other `perform_later`s) stays in before_update.
