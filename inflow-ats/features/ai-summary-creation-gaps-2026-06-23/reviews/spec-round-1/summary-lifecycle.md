# summary-lifecycle / state-machine — Round 1

Traced the `AiJobApplicationSummary` status machine + the parallel `AiJobApplicationSummaryStatus` row machine across model callbacks, the bridge, orchestrator, pipeline services, the C7/C8 side effects, and the FE that renders each state, for W1 (new `textract_processing` entry) + W5 (new `failed` row state + `record_failure` + C1 stale guard).

Chain traced: `job_application.rb:45,164-171` -> `create_auto_ai_summary_generation.rb (NEW)` (analog `create_ai_summary_generation.rb:30-53`) -> `submit_resume_to_textract.rb:18-27` -> `textract_result.rb:98-108,114-144` -> `get_resume_text_from_textract_job.rb:6-23` (C8) -> `ai_job_application_summary.rb:23,47-55,57-98,100-111` (C7 + writers) -> `ai_job_application_summary_status.rb:7,9-14` -> FE `PlatoTab.tsx:42-52,151-187` + `jobApplication.ts:4`.

## Findings

- **F1 [HIGH]** -- C8 / W5 choke-point are NOT reconciled; the auto-failed summary will NOT render a failed state on the detail card. SPEC.md W1/C8 (line 36) says `cleanup_orphaned_summary` should "transition the summary to `failed`" so the auto summary "persists as a visible failed state." SPEC.md W5 (line 117-119) defines `record_failure` as the single choke-point that sets the summary `failed` AND syncs the STATUS ROW to `failed` (pointing `ai_job_application_summary_id` at the failed summary), and says "Route ALL terminal summary-`failed` writes through it." But the W5 "Sites to convert" list does NOT include `cleanup_orphaned_summary`, and W1/C8 describes a bare `status: :failed` write, not a `record_failure` call.

  Why this breaks: on Textract terminal failure the bridge never fires (`textract_job_result_text` is never set on failure -- `get_resume_text_from_textract.rb` writes `update_columns(textract_job_status:'failed')`), so `set_initial_summary_pending` (`textract_result.rb:98-108`) never runs. The status row therefore stays `status: 'none'`, `ai_job_application_summary_id: nil`. If C8 only sets the SUMMARY to `failed` (not the row), then `PlatoTab.tsx:46` passes `aiJobApplicationSummaryId: summaryStatus?.aiJobApplicationSummaryId` = nil -> `useAiJobApplicationSummary` fires no fetch -> `fullSummary` undefined -> the existing `failed` branch (`PlatoTab.tsx:175-186`, guarded `fullSummary && fullSummaryStatus === "failed"`) does NOT render. With `hasResume` true, `:187` also fails, so the card falls through to the default empty state (`:197-206`, "ready"/"noCredits"). Net: the auto-failed candidate shows a "ready to generate" affordance, NOT a failed state -- contradicting D1 and SPEC.md W5 line 126.

  Fix: W1/C8 must route through the W5 `record_failure` choke-point (sets summary `failed` AND updates the status row to `failed` pointing at the summary). Add C8's summary-`failed` write to the W5 "Sites to convert" list, and reword W1/C8 to call `record_failure(error_message)` (keeping the manual-case `AI_SUMMARY_FAILED` broadcast for a non-nil requesting user). APPLIED.

- **F2 [MED]** -- `record_failure` must be exercisable from the C8 class-method context. `cleanup_orphaned_summary` is a CLASS method (`self.cleanup_orphaned_summary`, `get_resume_text_from_textract_job.rb:10-23`) holding the `summary` instance (`:14-15`). `summary.record_failure(...)` is fine. The status row exists in this path (created at intake by `enqueue_new_job_application:170`), so `record_failure`'s `return unless ai_job_application_summary_status` guard (SPEC.md line 120) passes. Spec should state C8 calls `summary.record_failure(...)` and the row is guaranteed to exist (no re-add of `find_or_create`). APPLIED (folded into F1 amendment).

- **F3 [MED]** -- The failed transition does not push to an already-open detail card; spec should acknowledge this so it is not later mistaken for a W4 gap or "fixed" wrongly. `record_failure` writes the SUMMARY side via `update_columns` (SPEC.md line 118, deliberately, to avoid rescue-path re-entrancy), bypassing `broadcast_status_change` (`ai_job_application_summary.rb:100-111`) even though `failed` IS in `BROADCAST_STATUSES` (`:23`). The STATUS-ROW `.update` has no broadcast callback. So `failed` emits no `ai_summary_status_change`. Auto path: acceptable (no watcher). Manual paths: the requesting user still gets a push via `GenerateAiJobApplicationSummaryJob#broadcast_completion` -> `AI_SUMMARY_COMPLETE` status:'failed' (`generate_ai_job_application_summary_job.rb:61,70`). Spec should note this so no one switches the summary write to `.update` (re-introducing re-entrancy). APPLIED (note added to W5).

- **F4 [LOW]** -- C7 cascade reasoning is correct; make the relink-vs-cascade invariant explicit in the test. `destroy_previous_textract_results` (`ai_job_application_summary.rb:47-55`) destroys only strictly-EARLIER non-succeeded results and cascade-destroys their summaries (`dependent: :destroy`, `textract_result.rb:5`). The W1 summary is relinked (`submit_resume_to_textract.rb:25-26`) to the SUCCEEDING result, so it survives even when an earlier failed `TextractResult` exists. Spec's C7 handling is adequate; the required test should include the "earlier failed TextractResult present" case. APPLIED (sharpened C7 test requirement).
