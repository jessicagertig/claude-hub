## Findings

- **F1 [MED]** -- The spec must require each converted failure site to PASS its existing `error_message` string to `record_failure`, unchanged. SPEC.md W5 (line 118) defines `record_failure(error_message)` and (line 119) lists sites to convert, but does not state that each site passes its CURRENT error_message string. The sites construct different strings: the `JSON::ParserError` branches use `"Failed to parse AI response: #{e&.message}"` (`generate.rb:180`, `score_job_application.rb:134`, `integrate_analysis.rb:64`); the `StandardError`/exhaustion branches use `e&.message` / `error&.message` (`generate.rb:184`, `score:138`, `integrate:68`, `generate_ai_job_application_summary_job.rb:19,44`); C8 uses `'Resume processing failed after multiple attempts.'`. An impl agent must call `summary.record_failure(<that exact string>)` at each site -- not drop it, not reconstruct it. Per the AI-credits Known Failure Patterns, fix agents mishandle error_message in payment/pipeline rescue paths; the spec should be explicit. Fix: add a line to W5 requiring each site to pass its existing error_message verbatim. APPLIED.

- **F2 [LOW]** -- Stale second copy of the status union in DEAD code (`PlatoOverviewCallout.tsx:13`). The component declares its own inline union `summaryStatusValue?: "none" | "initial_summary_pending" | "current" | "regenerating" | null` (`:13`), separate from `jobApplication.ts:4`. It is NOT imported or rendered anywhere (grep: zero importers, zero `<PlatoOverviewCallout` JSX). Its actual logic `deriveCalloutStatus` takes `string | null` (`:38`, loose), so there is no compile or functional risk today. NOT amended (no MED+ impact; amending dead code would add churn), but the W5 grep instruction should mention it so a future reviewer does not re-discover it as a phantom finding, and so that IF the component is ever wired, the union is updated. Documented here; no spec change required.
