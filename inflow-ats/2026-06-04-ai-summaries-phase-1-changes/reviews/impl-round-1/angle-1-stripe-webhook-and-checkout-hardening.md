# Stripe Webhook and Checkout Hardening — Round 1

## Findings

- F1 [HIGH] `app/jobs/stripe_webhook_handler_job.rb:212` / `invoice.paid` top-up handler passes invoice object as `session:` to `ApplyAiCreditPurchase.call(session: object, kind: :one_off)`, but `object` is the Stripe invoice (type `invoice.paid`), not a checkout session. Inside `ApplyAiCreditPurchase#apply_one_off` (line 41), `Stripe::Checkout::Session.list_line_items(session.id, limit: 1)` is called -- this Stripe API only accepts checkout session IDs, not invoice IDs. In production this will raise a `Stripe::InvalidRequestError` because `in_xxx` is not a valid checkout session ID. The test masks this by stubbing `Stripe::Checkout::Session.list_line_items` to accept the invoice ID `in_test_topup`. / Recommended fix: The invoice.paid handler should extract the price lookup_key directly from the invoice metadata (it's already there as `stripe_price_lookup_key`), look up the credits from `OrganizationAiCreditPurchase.credit_amount_for_key`, and create the purchase record directly -- OR pass the invoice as a different named parameter and have `apply_one_off` handle both paths. The spec must also be fixed to not mask this with an invoice-ID stub.

- F2 [MED] `app/jobs/stripe_webhook_handler_job.rb:61` / `checkout.session.completed` handler uses `update_columns` to set `stripe_subscription_id`, which bypasses validations and callbacks. While this is intentional to avoid validation issues on a pre-checkout record, it also means any `after_save` hooks on the model are skipped. This is a minor concern since there are no known callbacks on this model, but the pattern should be documented with a comment explaining why `update_columns` is used instead of `update`.

- F3 [MED] `spec/jobs/stripe_webhook_handler_ai_credits_spec.rb` / The invoice.paid top-up spec stubs `Stripe::Checkout::Session.list_line_items` with an invoice ID (`in_test_topup`), masking the production bug described in F1. Tests should not stub API calls with IDs of the wrong object type.
