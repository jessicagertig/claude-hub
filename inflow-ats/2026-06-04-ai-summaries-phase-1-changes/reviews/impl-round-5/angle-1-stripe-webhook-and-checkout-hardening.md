# angle-1: stripe-webhook-and-checkout-hardening — Round 5

## Findings

- F1 [HIGH] `app/interactors/apply_ai_credit_purchase.rb:84-130` / `apply_one_off_from_invoice` is a 46-line method with NO spec coverage / The spec (Note #4) says the `invoice.paid` branch for top-ups should "grant one-off credits using the `organization_id` and `stripe_price_lookup_key` from the invoice metadata." The existing `apply_one_off(session)` method already does this work. The user points out that the existing `board_wwr_listing_id` and `board_what_jobs_listing_id` branches in `invoice.paid` process one-off purchases inline -- no special interactor method needed. The `apply_one_off_from_invoice` method duplicates ~80% of `apply_one_off` (same org lookup, same balance check, same credit grant, same ledger write, same notification flags) with only the data source differing (invoice metadata vs session). This is textbook reinventing-the-wheel within the same file. / Recommended fix: The `invoice.paid` top-up branch in `stripe_webhook_handler_job.rb` (lines 211-220) could process the top-up inline (look up org, look up credits, create purchase, create ledger row) following the listing pattern. Alternatively, if the interactor is preferred, modify `apply_one_off` to accept either a session or invoice by extracting the data-source-specific fields into a params hash passed by the caller, eliminating the duplicated method entirely.

- F2 [HIGH] `app/models/organization_ai_credit_purchase.rb:53` / `stripe_checkout_session_id` validation relaxed for one-offs with `stripe_invoice_id` -- NOT in spec / The spec's validation relaxation section (Note #9B-5) covers ONLY subscription records: "Relax validations for pre-checkout state (subscription records created at checkout have no payment data yet)." The addition of `if: -> { one_off? && stripe_invoice_id.blank? }` on `stripe_checkout_session_id` is a fix-agent invention to support `apply_one_off_from_invoice`, which itself is out of spec. This validation change means one-off purchases can now be created without ANY session linkage -- just an invoice ID -- which breaks the idempotency model described in the spec (which uses `stripe_checkout_session_id` as the unique lookup key for one-offs).

- F3 [HIGH] `app/jobs/stripe_webhook_handler_job.rb:285-289` / `charge.refunded` handler with `handle_charge_refunded` is entirely new code NOT in spec / The spec mentions `ApplyAiCreditRefund` only in the context of Note #3 (fixing `.order(:created_at).first` to `.last` and removing `.reload`). There is no spec requirement for a `charge.refunded` webhook handler. The `handle_charge_refunded` method (lines 424-455) is 31 lines of new webhook routing logic with Stripe API calls (`Stripe::PaymentIntent.retrieve`, `Stripe::Invoice.retrieve`, `Stripe::Checkout::Session.list`) that were never specified, reviewed, or requested.

- F4 [HIGH] `app/jobs/stripe_webhook_handler_job.rb:114-136` / `customer.subscription.updated` AI credit branch is NOT in spec / The spec mentions `customer.subscription.updated` zero times. This 22-line branch intercepts credit pack subscription updates, looks up the purchase by `stripe_subscription_id`, and updates `subscription_status`, period dates, and `subscription_canceled_at`. This is entirely new webhook routing added by the fix agent.

- F5 [HIGH] `app/jobs/stripe_webhook_handler_job.rb:155-168` / `customer.subscription.deleted` AI credit branch is NOT in spec / Similarly, this 13-line branch intercepts credit pack subscription deletions and marks them canceled. Not in the spec.

- F6 [MED] `app/controllers/api/v1/organization_ai_credit_purchases_controller.rb:52` / `amount_cents_paid: 0` hardcoded on checkout / The spec says checkout creates a purchase with `kind: :subscription`, `stripe_checkout_session_id`, `stripe_price_lookup_key`, and `subscription_credits_per_period`. It does NOT say to set `amount_cents_paid: 0`. The validation was relaxed to allow nil `amount_cents_paid` for pre-checkout subscriptions (`unless: -> { subscription? && stripe_subscription_id.blank? }`), but the controller sets it to `0` anyway, which defeats the purpose of the relaxation and sets a misleading "paid $0" rather than "not yet paid."

- F7 [MED] `app/jobs/stripe_webhook_handler_job.rb:270-284` / `invoice.paid` error handling restructured beyond spec scope / The spec says nothing about restructuring error handling. The original code had a single `rescue StandardError` catch-all. The fix agent added a three-tier rescue (`Stripe::StripeError`, `ActiveRecord::RecordInvalid/RecordNotFound`, `StandardError` with re-raise). While defensible, re-raising on unexpected errors changes the retry behavior of the webhook handler. The comment says "re-raise so Sidekiq retries the webhook" -- but the original code intentionally swallowed all errors. This behavioral change was not specified.

- F8 [MED] `app/interactors/apply_ai_credit_purchase.rb:5-6` / Stale docstring: says one-off is called from `checkout.session.completed` / The docstring says "checkout.session.completed -> call(session: session, kind: :one_off)" but in the current implementation, one-off top-ups are called from `invoice.paid` with `call(invoice: invoice, kind: :one_off)`. The `checkout.session.completed` `mode == 'payment'` branch was removed per spec. The docstring describes a call path that no longer exists.
