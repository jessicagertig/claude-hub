# Extraction Service — Round 1

## Findings

- F1 [HIGH] Spec lines 156-162 / Flattening algorithm is unspecified. The spec says the service "flattens the structured data into `structured_extraction_text`" but never describes HOW. The structured extraction result is a nested JSON object with string fields (`name`, `email`, `professional_summary`), arrays of strings (`skills`, `certifications`, `links`), and arrays of objects (`work_experience` with 5 sub-fields each, `education` with 4 sub-fields each). The flattening algorithm directly determines search quality — whether skills are searchable, whether job titles within work_experience are findable, how array items are delimited, and whether JSON key names appear in the output text. The implementor has no guidance on: (a) which fields to include/exclude (should `links` URLs be searchable?), (b) how to handle nested objects (concatenate sub-fields? include field labels?), (c) what separator to use between sections (newlines? spaces? labeled sections?), (d) whether null fields are skipped or produce empty strings. / Evidence: review-angles line 72 explicitly calls this out ("verify flattening produces searchable text (all fields concatenated, no JSON syntax in output)") but the spec doesn't answer it. / Fix: add a "Flattening algorithm" subsection under the Service section specifying which fields are included, how nested objects are serialized, and the separator. Example: concatenate all non-null scalar fields and all array items (including sub-fields of work_experience and education objects), separated by spaces or newlines, with no JSON syntax.

- F2 [MED] Spec lines 156-162 / No mention of `AiApiRequest` tracking. The existing extraction (Call 1 in `AiJobApplicationAction::Summary::Generate#generate`) creates an `AiApiRequest` record via `create_ai_api_request` (generate.rb:56, 296-313) for every GPT-4o-mini call. The `AiApiRequest` model tracks: organization, requestable (polymorphic), call_type, provider, model, input_tokens, output_tokens, cost, prompt_text, response_body. The new service makes the same GPT-4o-mini call but the spec doesn't mention whether to create `AiApiRequest` records. If yes: `AiApiRequest.requestable` is `belongs_to :requestable, polymorphic: true` (required in Rails 5+), and the existing extraction uses `AiJobApplicationSummary` as the requestable. The new extraction has no `AiJobApplicationSummary` — `TextractResult` itself would be the natural requestable, but that requires adding `has_many :ai_api_requests, as: :requestable` to `TextractResult`. If no: the API cost goes untracked, breaking the auditing pattern. / Fix: spec must state whether `AiApiRequest` records are created, and if so, what the `requestable` is.

- F3 [MED] Spec line 117, lines 92-99 / `job_title` parameter not specified for new service. The spec says "uses the SAME prompt and schema" and the existing prompt's `messages` method accepts `resume_text:` (required) and `job_title:` (optional). The existing Call 1 passes both (generate.rb:46-48). The spec doesn't state whether the new service should pass `job_title`. At the call site (`GetResumeTextFromTextract#parse_resume_text`), the job title is accessible via `@job_application.job&.title`. For keyword search purposes, `job_title` biases the extraction toward role-relevant terms — unclear if that's desirable for a general search index. / Fix: explicitly state whether the new service passes `job_title` to the prompt and why.

- F4 [MED] Spec lines 156-162 / Service public method name not specified. Per `cursor_rules/backend/services.md` rule 2: "Use Descriptive Public Method Names — Not `call` or `execute`." The spec says "New service class (e.g., `ExtractStructuredResumeData`) that: Takes a TextractResult..." but doesn't name the public method. The implementor might use `call` (interactor pattern, not allowed for services) or `extract` (acceptable). Also per rule 3: "Pass IDs When Called from Background Jobs, Objects in Request Cycle." The call site determines whether to pass a TextractResult object or ID. / Fix: specify the public method name (e.g., `extract`) and whether the service takes a TextractResult object or ID.

- F5 [LOW] Spec line 117 / "Does NOT add `total_months_experience`" — correctly excludes this. The existing Call 1 adds `total_months_experience` to structured_data AFTER the extraction (generate.rb:60-62), computed from work_experience dates. This is a post-processing step, not part of the GPT schema. The spec correctly notes it doesn't belong in the keyword search extraction. No issue — noting for completeness.

## Amendments Needed

1. (F1 — HIGH) Add a "Flattening algorithm" subsection specifying how `structured_extraction` jsonb is converted to `structured_extraction_text` searchable text.
2. (F2 — MED) Add a statement on whether `AiApiRequest` records should be created for the new extraction call, and if so, what `requestable` to use.
3. (F3 — MED) Explicitly state whether `job_title` is passed to the prompt.
4. (F4 — MED) Specify the service's public method name and parameter type (object vs. ID).
