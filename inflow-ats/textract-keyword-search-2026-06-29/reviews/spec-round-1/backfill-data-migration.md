# Backfill Data Migration — Round 1

## Findings

- F1 [MED] Spec line 174 — **Backfill scoping should also guard on `textract_job_result_text` being present, not just `textract_job_status = succeeded`.** The spec says: "iterate existing `textract_results` where `textract_job_status = succeeded` and `structured_extraction IS NULL`." However, `resume_text_from_blocks` in `GetResumeTextFromTextract` (line 52) could theoretically return an empty string if no blocks have `block_type == 'LINE'` — the `update` would succeed with status `succeeded` but `textract_job_result_text` set to `""`. Calling GPT-4o-mini with empty text wastes money and produces garbage. The reference backfill uses `textract_job_result_text IS NOT NULL` as a guard. The new backfill should add `AND textract_job_result_text IS NOT NULL AND textract_job_result_text != ''` (or use `.where.not(textract_job_result_text: [nil, ''])` in ActiveRecord). Fix: Add `textract_job_result_text` presence check to the scoping clause.

- F2 [MED] Spec lines 174-176 — **Backfill does not specify batch size or rate limiting parameters.** The spec says "Batch with rate limiting since each record makes an API call" but provides no concrete values. An implementor needs to know: batch size (e.g., 100 records per batch), delay between API calls (e.g., `sleep 0.5`), and delay between batches. GPT-4o-mini has rate limits. Without guidance, an implementor might iterate all records as fast as possible and hit API rate limits, or use excessively conservative delays that make the backfill take days. Fix: Specify batch size (e.g., `find_each(batch_size: 100)`) and per-record delay (e.g., `sleep 0.2` between calls), or at minimum state "use `find_each` with a per-record sleep to stay under OpenAI rate limits."

- F3 [MED] Spec lines 173-176 — **Backfill as a data migration runs synchronously during deploy. With API calls per record, this could block deploys for hours.** The `data_migrate` gem runs data migrations during `rails db:migrate`. If there are thousands of textract results, each requiring a GPT-4o-mini call (~1-2 seconds each), the migration could take hours. This blocks the deploy pipeline. Consider: should the data migration only SET UP the backfill (e.g., enqueue a background job that processes records), or should the migration itself iterate? The reference backfill runs instantly because it's a single SQL UPDATE. The new backfill is fundamentally different — it's an API-call-per-record operation. Fix: The spec should either (a) specify that the data migration enqueues a one-time background job that does the actual backfill, or (b) explicitly acknowledge the deploy-time cost and confirm it's acceptable.

- F4 [LOW] Spec line 174 — **Backfill does not mention error handling for individual records.** If the GPT-4o-mini call fails for one record (timeout, rate limit, bad response), should the migration halt, skip that record and continue, or retry? The `IS NULL` guard handles resumability at the migration level (re-run picks up where you left off), but within a single run, the behavior on per-record failure is unspecified. Fix: Specify per-record error handling (e.g., "rescue, log the error and `textract_result.id`, continue to next record").
