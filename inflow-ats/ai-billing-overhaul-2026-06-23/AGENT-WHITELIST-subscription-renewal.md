# Subscription Renewal — Agent-Sanctioned Whitelist (flow 2)

Forced / no-analog deviations the audit/fix loop discovered and the orchestrating agent whitelisted to unblock convergence while the owner was away. The audit reads this file alongside `SANCTIONED-subscription-renewal.md` and does not flag anything listed here.

**Bar for inclusion:** the deviation is forced by our domain / data model / a genuine product difference between the AI-credit-pack subscription and the main plan, AND there is no way to match the analog without breaking correct behavior. NEVER whitelisted because a fix is hard. Each entry cites the analog it diverges from and why no match is possible. For Jessica's later audit.

---

1. **Extra grant-once idempotency guard keyed on `stripe_invoice_id`** — `apply_ai_credit_purchase.rb` `apply_subscription` has `return if organization_ai_credit_purchase.stripe_invoice_id == invoice.id`, which the analog (`ResetAiCredits#call`, `reset_ai_credits.rb`) does NOT have. Diverges from: the analog's per-renewal reset, which runs unconditionally every renewal with no invoice-id check. Why no match is possible: the analog grants by ZERO-THEN-RESET of the `:monthly` bucket (debit `monthly_credits_remaining` to 0, then credit `new_allocation`), so re-running the same renewal is self-correcting and idempotent by construction — no guard is needed. OURS grants ADDITIVELY: it inserts a single `:subscription_credit_pack_purchase_credit` credit of `subscription_credits_per_period` into the `:addon_subscription` bucket without first zeroing it. A duplicate `invoice.paid` delivery (Stripe redelivers) would therefore DOUBLE-GRANT credits. The grant-once guard on `stripe_invoice_id` is required for correctness and exists only because the credit-pack subscription's additive `addon_subscription` bucket is a different product from the main plan's reset-style `:monthly` allocation. Forced by the data-model/product difference, not whitelisted for convenience.

2. **No Stripe default-payment-method sync** — the analog else branch calls `organization.stripe_update_default_payment_method` (`stripe_webhook_handler_job.rb:269`), which makes a chain of Stripe API calls (`Subscription.retrieve` `organization.rb:477`, `PaymentMethod.retrieve` `:517`, `PaymentMethod.list` `:620-623`, `Customer.update` `:630-632`) to set the org-level `invoice_settings.default_payment_method` on the Stripe Customer from the MAIN-plan subscription's `default_payment_method`. OURS (`handle_subscription_credit_pack_invoice_paid` `stripe_webhook_handler_job.rb:448-466` + `ApplyAiCreditPurchase#apply_subscription` `apply_ai_credit_purchase.rb:24-80`) makes ZERO Stripe API calls beyond the shared `Stripe::Subscription.retrieve` and does no PM sync. Diverges from: the analog's `stripe_update_default_payment_method` call. Why no match is possible: `invoice_settings.default_payment_method` is a single org-level field on the Stripe Customer that the MAIN plan owns. `stripe_update_default_payment_method` derives `pm_id` from `organization.stripe_subscription` (the main-plan subscription, via `organizations.stripe_subscription_id`), NOT from the credit-pack subscription. Running it on a credit-pack renewal would overwrite (or, if the org has no main-plan subscription, fail/no-op on) the org's default payment method using the wrong subscription's PM. There is no credit-pack-specific org-level default-PM field to sync — the credit-pack subscription has its own Stripe PM but no analogous customer-level field of its own. Forced by the product/data-model difference (the org-level default PM is owned by the main plan), not whitelisted for convenience.

3. **Additive `addon_subscription` grant instead of reset-style `:monthly` allocation** — the analog calls `organization.organization_ai_credit_balance&.reset_ai_credits` → `ResetAiCredits` (`reset_ai_credits.rb:34-77`), which ZERO-THEN-RESETs the `:monthly` bucket (a `:plan_monthly_reset_debit` row of `-monthly_credits_remaining` `:40-49`, then a `:plan_monthly_allocation_credit` row of `new_allocation` from `resolve_allocation` `:52-63`), and sets `last_reset_at` + clears `low_credit_notification_sent_at` / `zero_credit_notification_sent_at` + the two `sent_*_since_increase` booleans (`:65-71`). OURS (`apply_ai_credit_purchase.rb:64-72`) inserts a single `:subscription_credit_pack_purchase_credit` row, bucket `:addon_subscription`, amount `organization_ai_credit_purchase.subscription_credits_per_period`, with no prior zero-out debit (additive grant), and clears only the two `sent_*_since_increase` booleans (`:74-77`), not setting `last_reset_at` and not clearing the two notification timestamps. Diverges from: `ResetAiCredits`'s reset-style `:monthly` allocation and its `last_reset_at` / notification-timestamp resets. Why no match is possible: the credit-pack subscription is a DIFFERENT PRODUCT whose credits live in the `:addon_subscription` bucket, which `ResetAiCredits` explicitly leaves untouched (`reset_ai_credits.rb:17` "The addon and addon_subscription buckets are intentionally untouched."). Adopting the reset mechanism would zero and re-allocate the MAIN plan's `:monthly` bucket — destroying the main plan's allocation — which is wrong for a credit-pack renewal. `last_reset_at` and the `*_notification_sent_at` timestamps are `:monthly`-bucket lifecycle fields owned by the main-plan reset; the addon_subscription grant has no equivalent monthly-reset semantics to set them by. Forced by the product/data-model difference (separate bucket, separate product), not whitelisted for convenience.
