# Subscription Change / Upgrade-Downgrade Portal — Agent-Sanctioned Whitelist (flow 5)

Forced / no-analog deviations the audit/fix loop discovered and the orchestrating agent whitelisted to unblock convergence while the owner was away. The audit reads this file alongside `SANCTIONED-subscription-change.md` and does not flag anything listed here.

**Bar for inclusion:** the deviation is forced by our domain / data model / a genuine product difference between the AI-credit-pack subscription and the main plan, AND there is no way to match the analog without breaking correct behavior. NEVER whitelisted because a fix is hard. Each entry cites the analog it diverges from and why no match is possible. For Jessica's later audit.

## W1. `determine_price_id` else-branch raises instead of resolving a default-plan price

- **Deviation:** OURS' `determine_price_id` keeps the analog's `if params.key?(:price_id)` guard, but its else-branch raises `StandardError, 'Price ID is missing.'` instead of resolving a fallback price.
- **Analog:** `app/controllers/api/v1/billing_controller.rb:630-640` — the else-branch does `Stripe::Price.list(...)` and returns `prices.data.find { |price| price.lookup_key == DEFAULT_PRICE_LOOKUP_KEY }` (`DEFAULT_PRICE_LOOKUP_KEY = 'plan_simple_ats_per_job_tiered'`).
- **Why no match is possible:** `DEFAULT_PRICE_LOOKUP_KEY` is a main-plan ATS price. There is NO single "default" AI-credit subscription plan — the AI-credit domain has multiple credit tiers and none is canonical/default. Resolving a main-plan ATS price here would be wrong (it would target the wrong product entirely), and there is no AI-credit constant to substitute. The frontend always posts `priceId` (`AiCreditSubscription.tsx` `handleSelectTier` → `tier.priceId`), so the else-branch is unreachable in practice; raising makes the absence loud rather than silently producing a `nil` Stripe `items.price`. The guard STRUCTURE (`params.key?(:price_id)`) is preserved to match the analog; only the unmatched fallback target is replaced with a raise.

## W2. `continue_url` base path is `/api/v1/ai_credit_purchases/...` not `/api/v1/billing/...`

- **Deviation:** In `update_payment_method_and_subscription_portal_session`, OURS builds `continue_url` pointing at `#{Variables::AtsRootUrl}/api/v1/ai_credit_purchases/continue_change_subscription_portal_session` rather than the analog's `/api/v1/billing/continue_change_subscription_portal_session`.
- **Analog:** `app/controllers/api/v1/billing_controller.rb:346` — `continue_url = "#{Variables::AtsRootUrl}/api/v1/billing/continue_change_subscription_portal_session" ...`.
- **Why no match is possible:** The continue endpoint is the AI-credit domain's own `continue_change_subscription_portal_session` action, mounted under `resource :ai_credit_purchases` in `config/routes.rb`. It lives at `/api/v1/ai_credit_purchases/continue_change_subscription_portal_session`, NOT under `/api/v1/billing`. Using the analog's `/api/v1/billing/...` literal would redirect the Stripe payment-method-update flow back into the MAIN-PLAN billing controller's continue action (operating on `current_organization.stripe_subscription_id`, the wrong subscription), breaking the AI-credit subscription-change handshake entirely. The path string must name OUR own route. Same forced cause as the domain-path/naming family in `SANCTIONED-subscription-change.md` #5; whitelisted here because it is a path literal not explicitly enumerated in that entry. No code change.

## W3. EXTRA `#show` action rendering the persisted `OrganizationAiCreditPurchase` row

- **Deviation:** OURS has an `#show` action (`app/controllers/api/v1/organization_ai_credit_purchases_controller.rb:4-13`, route `config/routes.rb:190` `resource :ai_credit_purchases, only: [:show]` → `GET /api/v1/ai_credit_purchases`) that authorizes `:organization_ai_credit_purchase, :show?`, looks up `current_organization.organization_ai_credit_purchases.subscription.find_by(subscription_status: [:active, :past_due])`, and renders the serialized persisted record via `Api::V1::OrganizationAiCreditPurchaseSerializer` (or `render json: nil`). The analog `BillingController` has NO `show` action — the current-subscription display is served exclusively by `customer_subscription`, which renders the LIVE Stripe object.
- **Analog:** `app/controllers/api/v1/billing_controller.rb` — no `show` action exists; `customer_subscription` (`:606`) renders `current_organization.stripe_subscription` (raw live Stripe object, no serializer).
- **Why no match is possible / not the symptom path:** `#show` is forced by the AI-credit data model: the AI-credit domain has a persisted `OrganizationAiCreditPurchase` row (the analog's `Organization` is always present and needs no separate "fetch the subscription purchase row" endpoint). `#show` is consumed by `AccountBillingAiCredits.tsx:39` (`useOrganizationAiCreditPurchase` → `GET /ai_credit_purchases`), a DIFFERENT view outside the subscription-change flow under audit. It is NOT on the subscription-change SCREEN path: `AiCreditSubscription.tsx` (the audited flow) does NOT import `useOrganizationAiCreditPurchase`; it gates the active-subscription display on the LIVE-Stripe `customer_subscription` payload (`AiCreditSubscription.tsx:53-70`), never on this `#show` record or its local `subscription_status` column — so `#show` does not reintroduce the local-column-gating defect. Deleting `#show` to match the analog would break `AccountBillingAiCredits.tsx`, a regression in a component outside the audited flow. Forced by the persisted-purchase-row data model (SANCTIONED #2 family); no code change.

## W4. Current-subscription credits value sourced from a local `lookupKey → credits` table, not the live Stripe price object

- **Deviation:** The active-subscription headline `{currentCredits?.toLocaleString()} credits / month` (`app/javascript/ats/src/views/accountAdmin/accountPlatoAi/AiSubscriptionStatus.tsx:35`) terminates on `currentCredits` (`AiCreditSubscription.tsx:66-70`), which resolves the live `currentPlanLookupKey` against `subscriptionTiers`; each tier's `credits` is injected from the LOCAL hardcoded table `AI_CREDIT_PACK_CREDITS_BY_LOOKUP_KEY` (`app/javascript/shared/lib/planHelpers.ts:74-87`, injected at `aiCreditPrices` `planHelpers.ts:115`). The analog has NO local price-id↔credits table — it round-trips the price id through Stripe and derives all current-plan values off the live Stripe object / persisted backend plan alias (`PlanFeatureGate`).
- **Analog:** trace price-model section ("The analog has NO local price-id↔credits/limits table … `PlanFeatureGate` keys all limits/features/AI-credit allocations off that alias string"); `app/controllers/api/v1/billing_controller.rb:537` (`Stripe::Price.list … expand: ['data.tiers']`).
- **Why no match is possible:** AI-credit allocation (credits-per-period) is AI-domain metadata that is NOT carried on the Stripe price object — there is no `tiers`/`unitAmount`→credits field on a flat per-period credit-grant price. The analog can derive limits backend-side from the persisted plan alias because the main plan's limits ARE keyed off the alias in `PlanFeatureGate`; the AI-credit per-period credit count has no such Stripe-resident or alias-resident source. The only place the lookupKey→credits mapping lives is this table (kept in sync with the backend model's `AI_CREDIT_AMOUNTS_BY_LOOKUP_KEY`, SANCTIONED #5). Matching the analog (no local table) would leave the credits headline with no data source. Forced; same `ai_credit_*` local-table family as SANCTIONED #5. Note: round-2 D1/D3 (nullable `?? null` local lookup driving credits + button text) is RESOLVED; this entry whitelists only the table's existence. No code change.

## W5. `AiCreditSubscription` rendered unconditionally; subscribed/unsubscribed fork relocated into a single dual-mode component

- **Deviation:** `app/javascript/ats/src/views/accountAdmin/OrganizationAiBilling.tsx:30` renders `<AiCreditSubscription pricesData={pricesData} />` UNCONDITIONALLY. The subscribed-vs-unsubscribed SCREEN fork lives DOWN inside `AiCreditSubscription` itself, gated on the live-Stripe-derived `isSubscribed` boolean (`AiCreditSubscription.tsx:59-60`), which drives `AiSubscriptionStatus`'s internal `isSubscribed ? … : …` branch (`AiSubscriptionStatus.tsx:32-52`) and the subtitle ternary (`AiCreditSubscription.tsx:283`). The analog gates its plans component in the PARENT via a 3-way `hasActiveSubscription` ternary with sibling components.
- **Analog:** `AccountBilling.tsx:122-134` — 3-way ternary: `eligibleForFreeTrial && hasActiveSubscription ?` → `AccountBillingPlansFreeTrial`; `: hasActiveSubscription ?` → `AccountBillingPlans`; `: (` else → `AccountBillingPlansUnsubscribed`. `AccountBillingPlans` is reached ONLY for an active-subscription, non-free-trial org.
- **Why no match is possible:** The analog's parent-owned 3-way fork exists because the main plan has a free-trial product variant (`AccountBillingPlansFreeTrial`) and a distinct unsubscribed component (`AccountBillingPlansUnsubscribed`). The AI-credit subscription has NEITHER — there is no AI-credit free trial, and the unsubscribed state ("No active subscription / Subscribe to start reviewing") is rendered INSIDE the same `AiSubscriptionStatus` component rather than a sibling. Reproducing the analog's parent 3-way split would require inventing a free-trial sibling and an unsubscribed sibling that have no product counterpart. The unsubscribed state IS rendered (not dropped), and crucially `isSubscribed` is derived from the LIVE Stripe object (the exact terminal whose column-gated mismatch produced the original symptom — now correct). Forced product simplification (single dual-mode AI-billing screen, no free-trial/unsubscribed siblings); the data-row scoping driving `isSubscribed` is SANCTIONED #4. No code change.
