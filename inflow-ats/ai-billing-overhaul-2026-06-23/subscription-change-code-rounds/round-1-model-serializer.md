## D1 — Active-subscription DISPLAY is sourced from a serialized LOCAL column, not the live Stripe subscription (root cause of the named symptom)

ANALOG (trace):
The current-subscription display is derived ENTIRELY from the LIVE Stripe subscription object. `customer_subscription` (`billing_controller.rb:606-618`) renders the raw `current_organization.stripe_subscription` (`Organization#stripe_subscription` `organization.rb:474-478` → `Stripe::Subscription.retrieve`), NO serializer (trace item 6/7). The frontend then reads display state off that live object: `currentSubscription?.status === "trialing"` (`:370`), `currentSubscription?.cancelAtPeriodEnd` (`:384`), `currentSubscription.items.data[0].price` (`:67`), period/renewal off the live object, `isCurrentPlan = currentSubscription?.plan?.id === plan.priceId` (`:436`) (trace item 9). There is NO analog serializer exposing a local `subscription_status` / `subscription_credits_per_period` / `subscription_current_period_end` column to gate "is there an active subscription / which tier / renews-when." The org serializer's `stripe_subscription_status` (`organization_serializer.rb:23`) is NOT what drives the AccountBillingPlans current-subscription block — that block reads `currentSubscription` (live Stripe).

OURS:
The active-subscription display is gated on serialized LOCAL columns of the `OrganizationAiCreditPurchase` row, not the live Stripe object. `OrganizationAiCreditPurchaseSerializer` exposes `subscription_status` (`:12`), `subscription_credits_per_period` (`:11`), `subscription_current_period_end` (`:14`), `subscription_canceled_at` (`:15`). `#show` (`controller:4-13`) serializes the local row and the frontend derives the entire `AiSubscriptionStatus` display from it: `isSubscribed = subscription?.subscriptionStatus === "active" || "past_due"` (`AiCreditSubscription.tsx:59`), `currentCredits = subscription?.subscriptionCreditsPerPeriod` (`:60`), `periodEndsAt = subscription?.subscriptionCurrentPeriodEnd` (`:263`), all rendered in `AiSubscriptionStatus.tsx:28-48`. The live Stripe object (`useAiCreditCustomerSubscription` → `customer_subscription` → `stripe_subscription`) IS fetched but is used ONLY for `currentSubscriptionItemId` (`:58`) and `isCurrent = currentSubscription?.plan?.id === tier.priceId` (`:272`) — NOT for the active/credits/renews display. So whenever the local `subscription_status` column is stale or unset (it is written only by webhook interactors — `apply_ai_credit_purchase.rb:55`, `apply_ai_credit_refund.rb:39`, `cancel_ai_credit_subscription.rb:35`), an actually-active Stripe subscription does NOT display. This is exactly the reported symptom: "an active subscription does NOT display; the analog derives the current-subscription display from the live Stripe subscription, ours gates on a local subscription_status column."

The model + serializer layer is the load-bearing mechanism: the serializer (`organization_ai_credit_purchase_serializer.rb:12-15`) is the source-of-truth feed for the display state, and the `subscription_status` enum (`organization_ai_credit_purchase.rb:83-85`) is the local column being gated on. To match the analog, the active-subscription display state (subscribed?, current credits/tier, renews-at) must derive from the live Stripe subscription object already returned by OUR `customer_subscription` / `OrganizationAiCreditPurchase#stripe_subscription` (which itself matches the analog), not from these serialized local columns. NOT covered by SANCTIONED/WHITELIST: #2 sanctions OPERATING on the purchase row (vs org columns) and #4 sanctions the live-subscription endpoint being scoped to `purchase.stripe_subscription_id` — neither sanctions sourcing the DISPLAY from the local `subscription_status` column instead of the live Stripe object.
