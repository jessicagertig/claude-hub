# Spec Review: TypeScript Type Safety -- AiAssessment Interface

**Reviewer angle:** TypeScript type correctness against live backend data  
**Spec file:** `~/claude-hub/inflow-ats/2026-06-11-ai-display/SPEC.md` (Section 7, lines 164-183)

## Findings

- F1 [MED] `AiAssessment` interface omits `tertiaryDomain` / The backend JSON schema (`resume_assessment.rb` lines 82-90, 117) defines `tertiary_domain` as a **required** field. It is always present in every assessment object. After `allKeysToCamel` transformation (`structure.js` line 49) it arrives on the frontend as `tertiaryDomain: { name: string | null; reasoning: string }`. The spec's `AiAssessment` interface (SPEC.md line 171-178) omits it entirely. While the Plato tab UI does not consume `tertiaryDomain`, the interface purports to type the assessment object's shape. An implementing agent reading the type would reasonably assume the field does not exist. If any future code tries to access `structuredData.assessment.tertiaryDomain`, TypeScript will flag it as a type error even though the data is present. / **Fix:** Add `tertiaryDomain: { name: string | null; reasoning: string } | null;` to the `AiAssessment` interface. (The `| null` accounts for the `name` nullability at the domain object level, matching the pattern used for `primaryDomain` and `secondaryDomain`.)

- F2 [LOW] `reasoning` typed as optional but backend schema requires it / The spec types `primaryDomain` and `secondaryDomain` as `{ name: string; reasoning?: string }` with `reasoning` optional. The backend JSON schema (`resume_assessment.rb` lines 68-71, 77-79) has `reasoning` in the `required` array for both `primary_domain` and `secondary_domain`, and the schema uses `strict: true` with `additionalProperties: false`. The AI model is forced to produce `reasoning` for every response. Typing it as optional (`reasoning?`) is technically safe (non-optional fields satisfy optional constraints), but it is inaccurate -- it signals to consuming code that `reasoning` might be absent when it never will be. / **Fix:** Change to `reasoning: string` (non-optional) for all three domain objects. This is cosmetic correctness and won't cause runtime issues either way.

- F3 [LOW] Nullable union type on `primaryDomain` and `secondaryDomain` is overly defensive / The spec types these as `{ name: string; reasoning?: string } | null`. The backend JSON schema requires both `primary_domain` and `secondary_domain` as top-level required fields (`resume_assessment.rb` line 117: `required: %w[primary_domain secondary_domain ...]`) with strict schema enforcement. Both objects are always present with non-null `name` values. Only `tertiary_domain.name` can be null (line 85: `type: %w[string null]`). The `| null` union is overly cautious for `primaryDomain`/`secondaryDomain` while being accurate for `tertiaryDomain.name`. / **Fix:** This is a judgment call. Keeping `| null` is a reasonable defensive pattern against future data issues, but the spec should note that it's defensive rather than reflecting actual backend behavior. Not blocking.

- F4 [LOW] `keySkills` and `standoutAccomplishments` typed as non-optional is correct / The backend JSON schema (`resume_assessment.rb` lines 107-115, 117) requires both `key_skills` and `standout_accomplishments` as top-level required arrays. They are always present. They can be empty arrays (per prompt instructions: "can be empty"). The spec's non-optional `string[]` typing is correct. The UI handles empty arrays with "omit section" logic (SPEC.md lines 71, 74: "Omit entire section if empty array"). No finding -- confirming correctness.

- F5 [LOW] `AiJobApplicationSummaryFeedItem.tsx` does NOT access `assessment` -- type refinement is non-breaking / Verified by reading the full component (lines 1-444). The component accesses `structuredData.workExperience`, `structuredData.education`, `structuredData.skills`, and `structuredData.certifications` (lines 73-79). It never accesses `structuredData.assessment`. The `assessment?: any` -> `assessment?: AiAssessment` refinement cannot break this component. Additionally, grep across all frontend `.tsx`/`.ts` files confirms no other file accesses the `assessment` property on structured data. The spec's claim that this is a "non-breaking type refinement" (SPEC.md line 183) is accurate.

- F6 [LOW] `comparison` field also typed as `any` but spec does not address it / `AiResumeStructuredData` has `comparison?: any` (line 32). The backend stores a comparison object with `applicable_experience`, `gaps`, and `overlap_summary` (`resume_comparison.rb` lines 27-33). However, Call 4 (`ResumeSummary`) re-produces these same three fields and they are merged into `structured_data` at the top level (`generate.rb` lines 155-160) as `roleAnalysis`, `applicableExperience`, `gaps`, `overlapSummary`. The UI consumes the top-level versions, not the nested `comparison` sub-object. Typing `comparison` would be completeness work only, with no UI impact. No fix needed for this spec -- this is future cleanup.

## Summary

One MED finding (F1: missing `tertiaryDomain`), two LOW accuracy findings (F2: `reasoning` optionality, F3: nullable union defensiveness), and three confirmations of correctness (F4, F5, F6). No BLOCKERs or HIGHs. The type refinement is non-breaking as claimed.
