# Spec Review: Emotion Styling Fidelity -- Theme Tokens, Dark Mode, Accent Gradient

## Findings

- F1 [MED] Spec section 5 (JobApplicationSidebar) / linkStyles missing details / The spec says the custom PlatoNavItem must "match the existing NavItem styling exactly: 40px height, `theme.poly.radii.sm` border-radius, same margins/padding, same `.active` and `:hover` states" and references `linkStyles` lines 56-95. The actual `linkStyles` (NavItem.tsx lines 55-94) also includes: (a) no base `color` declaration -- the default text color is inherited, not explicitly set; (b) `text-decoration: none`; (c) `transition: background-color 0.2s ease` (not just any transition); (d) the `> svg` base styles (`transition: opacity 0.2s ease; flex-shrink: 0; opacity: 0;`) that control chevron visibility; (e) a responsive breakpoint `${breakpoint.sm}` that gates `:hover` behavior so it only applies at `sm` breakpoint and above; (f) within hover, `> svg { stroke: ${props.theme.poly.color.secondaryText}; opacity: 1; }` (explicit stroke color on the chevron). The spec omits (b), (d), (e), and (f). An implementor copying only the spec's description would miss the responsive hover gating and the chevron show/hide pattern. / Amend the spec to either say "copy `linkStyles` verbatim and adapt only the icon slot" or enumerate the missing properties, especially the breakpoint-gated hover and the `> svg` opacity pattern.

- F2 [MED] Spec section 5 (JobApplicationSidebar) / linkStyles also relies on `StyledLabel` wrapper / The spec says to match NavItem styling but only references `linkStyles`. The actual NavItem also has a `StyledLabel` styled component (lines 103-118) that wraps the icon + text, providing `display: flex; align-items: center; overflow: hidden;` plus `Text` child truncation (`white-space: nowrap; overflow: hidden; text-overflow: ellipsis;`) and `svg { margin-right: 8px; flex-shrink: 0; }`. The PlatoNavItem needs an equivalent inner wrapper for the PlatoChip + "Plato" label to align correctly. / Amend the spec to note the PlatoNavItem needs both the outer link styles AND an inner label-wrapper matching `StyledLabel`.

- F3 [LOW] Spec section 4 (PlatoTab, Eyebrow style) / Eyebrow color differs from analog / The spec says eyebrow color is `${theme.poly.color.secondaryText}` and says to follow `AiJobApplicationSummaryFeedItem` `Styled.SectionTitle` (lines 317-326). But the analog uses `${t.dark ? t.color.gray[400] : t.color.gray[500]}` -- in light mode, that is `gray[500]`, while `poly.color.secondaryText` resolves to `gray[600]`. In dark mode both resolve to `gray[400]`, so the discrepancy is light-mode only. The spec's recommendation (`secondaryText`) is the more modern Poly DS approach, but it does NOT match the analog it references. / Acknowledge the intentional upgrade from `gray[500]` to `secondaryText` (`gray[600]`) or switch to the analog's exact value. Either is fine, but the spec currently says "follow the analog" while specifying a different color.

- F4 [LOW] Spec section 4 (PlatoTab, "Fit for this role" card) / 9px radius has no theme token / The spec says "9px radius" for the Fit card border. The `poly.radii` scale is `xs: "4px", sm: "5px", md: "7px", lg: "13px"` -- there is no 9px token. This is a raw value that sits between `md` (7px) and `lg` (13px). This is fine if intentional (design-specified), but breaks the "prefer Poly DS tokens" constraint stated in the Dark Mode section. / Confirm 9px is the design intent (not 7px/md or 13px/lg), or map it to the nearest token.

- F5 [LOW] Spec section 4 (PlatoTab, Headline) / 23px font size has no theme token / The spec says the headline is "23px, line-height 1.28, weight 600, letter-spacing -0.02em." The `typeScale` tokens are: `xs` (0.75rem/12px), `sm` (0.875rem/14px), `base` (1rem/16px), `lg` (1.125rem/18px), `xl` (1.25rem/20px), `xxl` (1.5rem/24px), `xxxl` (1.875rem/30px). 23px is not close to any token (nearest is `xxl` at 24px). There is also no heading token that matches: `t.text.h2` is `600 weight + xxl (24px)`. The spec correctly does NOT reference a theme token for this, but the implementor should know 23px is an intentional design-specific value and must be a raw `font-size: 23px;` declaration (NOT `${t.text.xxl}` which would give 24px). / No change needed, but worth noting for the implementor that this is an explicit raw value, not a near-miss typo for `t.text.xxl`.

- F6 [LOW] Spec section 4 (PlatoTab, Eyebrow style) / `t.text.xs` usage instruction is ambiguous about inline vs standalone / The spec says "Use `t.text.xs` for size." Known Failure Pattern #1 warns that `t.text.xs` is a complete CSS declaration (`font-size: 0.75rem;`) and must be used standalone, not inside `font-size: ${t.text.xs};`. The analog (`Styled.SectionTitle`) uses it correctly: `${[t.mb(2), t.text.xs]}` (array spread, standalone). The spec's phrasing "Use `t.text.xs` for size" is not wrong, but an implementor unfamiliar with the pattern might write `font-size: ${t.text.xs};`. / Amend to say "Spread `t.text.xs` standalone (as in the analog), not inside a `font-size:` property" or cite the Known Failure Pattern.

- F7 [LOW] Spec section 3 (PlatoOverviewCallout) / `theme.poly.radii.md` reference is correct but could be confused with `t.rounded.md` / The spec says the callout card uses `theme.poly.radii.md` radius (7px). This is the raw string value `"7px"` from `poly.radii.md`, suitable for `border-radius: ${theme.poly.radii.md}`. This is correct. However, `t.rounded.md` is also 7px but as a complete CSS declaration (`border-radius: 0.4375rem;`). An implementor could confuse the two, and using `t.rounded.md` standalone would also work (but produces a `rem` value instead of `px`). The spec is correct as-is. The "Fit for this role" card (section 4 item 5) says "9px radius" without referencing any token, which is consistent since 9px has no token. / No change needed. Noting for completeness that both `poly.radii.md` and `t.rounded.md` resolve to 7px; the spec correctly uses the raw-value form for inline `border-radius` property usage.

- F8 [MED] Spec section 4 (PlatoTab, Skills chips) / dark mode fill for key-skill chips uses raw color without Poly DS token / The spec says key-skill chips have `colors.gray[100]` fill in light mode and `colors.gray[700]` in dark mode. This requires a `t.dark` ternary: `background: ${t.dark ? t.color.gray[700] : t.color.gray[100]}`. This is correct for the codebase's capabilities -- there is no Poly DS token that maps to "chip fill" (`chipCanvas` does not exist in either light or dark poly themes). However, the spec's Dark Mode section says "Prefer Poly DS tokens where they exist" and then lists a `t.dark` ternary fallback for cases Poly DS doesn't cover. The spec should explicitly note that chip fill requires a `t.dark` ternary since no `chipCanvas` token exists, rather than leaving the implementor to discover this. / Add a brief note next to the chip fill colors that these require `t.dark` ternary because there is no `chipCanvas` or equivalent Poly DS token.

- F9 [MED] Spec section 4 (PlatoTab, Skills chips) / non-key-skill "transparent fill" needs dark mode consideration / The spec says non-key skill chips have "transparent fill." In light mode on a white card background, transparent is fine. In dark mode, the card background is `gray[800]` (from `poly.color.cardCanvas`). A transparent chip on `gray[800]` with a `chipBorder` of `gray[700]` (dark) will look like a very subtle outlined chip -- barely visible border contrast (700 on 800). This may be the design intent, but it differs significantly from the light-mode appearance where `chipBorder` `gray[300]` on white has strong contrast. / Verify the design intent for non-key chip visibility in dark mode. If stronger contrast is needed, consider a `t.dark ? colors.gray[900] : 'transparent'` fill or a lighter `chipBorder` override.

## Summary

No BLOCKERs or HIGHs. Three MEDs: (F1) linkStyles description omits responsive hover gating and chevron visibility pattern, (F2) PlatoNavItem needs the inner StyledLabel wrapper not just linkStyles, (F8/F9) chip dark-mode styling needs explicit `t.dark` ternary guidance and contrast verification. Six LOWs covering theme token gaps and clarification opportunities.
