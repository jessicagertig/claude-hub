# Structured Data Access Review

## Findings

- F1 [HIGH] Spec line 66, item 1 (Provenance line) / `timeAgoInWordsShort(aiSummary.createdAt)` will produce NaN / `timeAgoInWordsShort` at `shared/lib/time.ts` line 14-26 does `datetime * 1000` and passes the result to `formatDistanceToNow`. The `createdAt` field on `AiJobApplicationSummary` is an ISO 8601 string (the serializer at `app/serializers/api/v1/ai_job_application_summary_shallow_serializer.rb` line 4 exposes `created_at`, which Rails serializes as an ISO string; the model at `app/models/ai_job_application_summary.rb` does NOT include the `PrettyTimes` concern that provides `created_at_timestamp`). The TypeScript type at `shared/types/aiJobApplicationSummary.ts` line 7 confirms: `createdAt: string`. Multiplying a string by 1000 yields `NaN`, and `formatDistanceToNow(NaN)` throws `RangeError: Invalid time value`. Every other callsite of `timeAgoInWordsShort` in the codebase uses a dedicated `createdAtTimestamp: number` field (e.g., `NotificationListItem.tsx` line 28 types it as `number`; the `PrettyTimes` concern at `app/models/concerns/pretty_times.rb` line 11-13 produces it via `created_at.to_i`). / Fix: either (a) use `formatDistanceToNow(parseISO(aiSummary.createdAt))` with the `parseISO` already imported in `shared/lib/time.ts` line 3, or (b) write a small helper like `timeAgoFromISO` that parses the ISO string. Do NOT pass `createdAt` to `timeAgoInWordsShort` -- the function signature expects a Unix-seconds number. Also update spec line 245 which repeats this instruction.

- F2 [HIGH] Spec line 69, item 4 (Domain label) / snake_case field paths `structuredData.assessment.primary_domain.name` and `structuredData.assessment.secondary_domain.name` are wrong for frontend code / The `apiGet` function at `shared/queryHooks/api.ts` line 22 applies `allKeysToCamel(data)` which deeply transforms all keys. The correct frontend access paths are `structuredData.assessment.primaryDomain.name` and `structuredData.assessment.secondaryDomain.name`. An implementer following the spec literally would access undefined properties, producing silent `undefined` renders with no error. / Fix: change line 69 to use `structuredData.assessment.primaryDomain.name` and `structuredData.assessment.secondaryDomain.name`.

- F3 [HIGH] Spec line 71, item 6 (Notable achievements) / snake_case field path `structuredData.assessment.standout_accomplishments` is wrong for frontend code / Same `allKeysToCamel` transformation applies. The correct path is `structuredData.assessment.standoutAccomplishments`. / Fix: change to `structuredData.assessment.standoutAccomplishments`.

- F4 [HIGH] Spec line 74, item 9 (Skills) / snake_case field path `structuredData.assessment.key_skills` is wrong for frontend code / Same `allKeysToCamel` transformation applies. The correct path is `structuredData.assessment.keySkills`. / Fix: change to `structuredData.assessment.keySkills`.

- F5 [HIGH] Spec line 7 (Summary paragraph) / four snake_case field references in the summary text: `assessment.key_skills`, `assessment.primary_domain.name`, `assessment.secondary_domain.name`, `assessment.standout_accomplishments` / These are the same fields flagged in F2-F4 above. The summary paragraph is the first thing an implementer reads and sets the mental model for field access paths throughout the entire component. Snake_case here will propagate into code. / Fix: update all four references in the summary to camelCase: `assessment.keySkills`, `assessment.primaryDomain.name`, `assessment.secondaryDomain.name`, `assessment.standoutAccomplishments`.

- F6 [LOW] Spec Section 7 (AiAssessment interface, lines 170-178) / `tertiaryDomain` omitted from the TypeScript interface / The backend `structured_data` blob includes `tertiary_domain` (from Call 1 assessment output), which becomes `tertiaryDomain` after `allKeysToCamel`. The spec's `AiAssessment` interface lists `primaryDomain` and `secondaryDomain` but not `tertiaryDomain`. The UI does not consume it, so this is not a runtime bug. However, accessing `assessment.tertiaryDomain` later would be a type error, and the interface is described as a proper typing of the assessment object. / Fix: add `tertiaryDomain: { name: string; reasoning?: string } | null;` to the `AiAssessment` interface for completeness. If intentionally omitted, add a code comment noting the omission.

## Verified correct

- C: Item 5 (Fit for role) uses `structuredData.roleAnalysis` with fallback to `aiSummary.summaryText`. Both paths are correct. `roleAnalysis` is declared at `AiResumeStructuredData` line 26 as `roleAnalysis?: string` (already camelCase in the TypeScript type). `aiSummary.summaryText` is on the shallow summary type at line 4 as `summaryText: string | null`. Access paths are valid.

- D (partial): Item 9 (Skills) uses `structuredData.skills` for the chip list. This is correct -- `skills` is a single word, no case transformation needed, and it exists at `AiResumeStructuredData` line 23 as `skills: string[]`. The `assessment.key_skills` part is wrong (see F4).

- Items 7 and 8: `structuredData.applicableExperience` (line 72) and `structuredData.gaps` (line 73) are both correct camelCase paths matching the TypeScript type at lines 27-28.
