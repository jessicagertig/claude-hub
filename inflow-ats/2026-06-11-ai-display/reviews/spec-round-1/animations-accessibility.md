# Spec Review: CSS Animations & Accessibility

**Spec:** `~/claude-hub/inflow-ats/2026-06-11-ai-display/SPEC.md`
**Angle:** Shimmer/dots animations, prefers-reduced-motion, keyboard accessibility, ARIA
**Codebase:** `/Users/jessica/wrk/wrk-corp/inflow-ats.ai-display`

## Findings

- F1 [MED] Shimmer keyframes missing `background-position` from/to values / The spec (line 227) gives the gradient, background-size, and animation timing (`linear-gradient(90deg, gray[100], gray[200], gray[100])`, `background-size: 600px 100%`, `animation: 1.4s ease-in-out infinite`) but never specifies what the keyframes animate. A shimmer effect requires `background-position` to sweep from left to right (e.g., `0% { background-position: -600px 0 }` to `100% { background-position: 600px 0 }`). Without this, an implementer must guess or look up the standard shimmer pattern. The existing codebase keyframes (Button `loadingAnimation` at lines 349-357, LoadingIndicator at lines 84-91, GrowlNotification at lines 127-149) all specify their from/to values explicitly. / Add the keyframes definition: `@keyframes shimmer { 0% { background-position: -600px 0; } 100% { background-position: 600px 0; } }`.

- F2 [LOW] Dot animation keyframes values not specified / The spec (line 229) says "pulsing opacity and slight Y translation over 1.1s" but does not give the keyframe percentages or values (e.g., `0% { opacity: 0.4; transform: translateY(0) }`, `50% { opacity: 1; transform: translateY(-3px) }`, `100% { opacity: 0.4; transform: translateY(0) }`). The existing `sk-bouncedelay` keyframes in `LoadingIndicator/styles.scss` (lines 45-56) use scale-based animation for dots -- a close analog but not identical to the spec's "opacity + Y translation" description. An implementer could reasonably derive this, but the shimmer finding (F1) is the more critical gap. / Optionally add the keyframe values, or reference the `sk-bouncedelay` pattern in `LoadingIndicator/styles.scss` as a starting point and note how the new animation differs (opacity+translateY vs scale).

- F3 [HIGH] No `prefers-reduced-motion` pattern exists in the codebase -- spec gives no implementation guidance / `grep -rn "prefers-reduced-motion" app/javascript/` and `grep -rn "prefers-reduced-motion" app/assets/` return zero results. The codebase has never implemented this media query. The spec (lines 81, 225, 258) says "Both animations must have `@media (prefers-reduced-motion: reduce) { animation: none; }`" but does not specify HOW to do this in Emotion. There are two valid approaches: (a) nest the `@media` query inside each styled component's `css` template literal, or (b) use Emotion `Global` component to inject a blanket rule. The spec mentions both `keyframes` and `Global` (line 225) but does not choose. Since there is no existing pattern to copy, the implementer will have to invent one, risking inconsistency with future reduced-motion handling. / Specify the approach. Recommended: nest `@media (prefers-reduced-motion: reduce) { animation: none; }` inside each animated styled component's `css` block (this is the standard Emotion pattern and keeps the rule co-located with the animation). This also establishes the codebase's first `prefers-reduced-motion` pattern for future components.

- F4 [HIGH] Spec says "Feather icons do this [aria-hidden] by default via the Icon component" -- this is incorrect / The `Icon` component at `app/javascript/ats/src/components/shared/Icon/index.js` (lines 12-23) renders `react-feather` icons but does NOT pass `aria-hidden="true"`. It renders `<SelectedIcon css={...} />` with no ARIA attributes. The `react-feather` library itself does not add `aria-hidden` to its SVGs either -- the dist output (checked `activity.js`) renders `<svg>` with no ARIA attributes, passing only `{...rest}` from props. The spec's claim at line 257 that "Feather icons do this by default via the Icon component" is factually wrong. This matters because the spec relies on this assumption to justify not adding explicit `aria-hidden` to icons. / Correct the spec: either (a) add `aria-hidden="true"` explicitly to the `PlatoMark` component's SVG elements AND note that existing Feather icons also lack `aria-hidden` (a pre-existing issue outside this feature's scope), or (b) update the `Icon` component to pass `aria-hidden="true"` as part of this feature (broader scope change). Option (a) is the minimal correct fix for this spec's scope.

- F5 [MED] Spec does not mention `aria-hidden="true"` in PlatoMark component description (Section 1) / The `PlatoMark` component description (lines 28-37) says nothing about accessibility attributes on the SVG. The `aria-hidden="true"` requirement appears only in the Accessibility section (line 257). An implementer reading Section 1 to build the component could easily miss the Accessibility section's requirement. / Add `aria-hidden="true"` to the PlatoMark SVG element requirements in Section 1 (line 32 area), so the requirement is at the point of implementation, not only in a separate section.

- F6 [MED] Callout card clickability: spec offers two approaches without choosing / The spec (line 259) says the callout card "should use a `<button>` or have `role=\"button\"` and `tabIndex={0}` with keyboard event handling." The codebase has both patterns: `CollapsibleItem.tsx` uses `role="button"` + `tabIndex="0"` + `onKeyDown` on a `div`, and `ContentWrapper/index.js` uses an actual `<button>`. For a clickable card with custom styling (border, radius, background, gradient bar), using a native `<button>` requires resetting all default button styles (`appearance: none; background: none; border: none; padding: 0; text-align: left; width: 100%; cursor: pointer; font: inherit;`). The `role="button"` approach avoids the reset but requires implementing keyboard handling. / Choose one approach. Recommended: use a `<button>` with a reset styled component (this is more semantically correct, gets keyboard handling for free, and the codebase already uses `<button>` in `ContentWrapper`). Specify that the styled component must include the button reset CSS. Note: if following the `CollapsibleItem` pattern (`role="button"` + `onKeyDown`), the keyboard handler should check `event.key === " "` (a space character), NOT `event.key === "Space"` -- the existing `CollapsibleItem.tsx` line 35 uses `"Space"` which is incorrect per the KeyboardEvent spec and silently breaks Space-key activation.

- F7 [LOW] NavLink `aria-current` is sufficient for nav accessibility / The spec (line 260) says "The Plato tab nav item must be a proper `NavLink` for keyboard navigation and screen reader accessibility." React Router's `NavLink` adds `aria-current="page"` to the active link automatically. The existing `NavItem.tsx` (line 101) uses `NavLink` with no additional ARIA attributes, and the spec's custom `PlatoNavItem` also uses `NavLink` (line 141). This is sufficient -- `NavLink` handles `aria-current`, and as an `<a>` element it is natively keyboard-focusable and activatable. No additional ARIA attributes are needed. / No fix needed. The spec is adequate on this point.

## Summary

2 HIGH, 3 MED, 2 LOW.

The two HIGHs are:
1. **F3**: No existing `prefers-reduced-motion` pattern in the codebase, and the spec does not specify the Emotion implementation approach. The implementer must invent a pattern with no analog to follow.
2. **F4**: The spec's claim that the Icon component adds `aria-hidden="true"` to Feather icons is factually wrong -- neither the `Icon` wrapper nor `react-feather` adds this attribute. The PlatoMark SVGs will lack `aria-hidden` unless explicitly added.
