## New findings

- F1 [HIGH] Spec lines 68, 264 / `formatDistanceToNow` missing `{ addSuffix: true }` / The spec recommends `formatDistanceToNow(parseISO(aiSummary.createdAt))` but `formatDistanceToNow` without the `addSuffix` option returns bare text like "3 days", not "3 days ago". The codebase's own `distanceInWords` function (`@shared/lib/time.ts` line 89-90) already handles this by passing `{ addSuffix: true }` and accepts ISO strings via `new Date(date)`. Without `addSuffix`, the provenance line will read "Generated by Polymer Plato . 3 days" instead of "Generated by Polymer Plato . 3 days ago". / Fix: Either (a) change both lines to say `formatDistanceToNow(parseISO(aiSummary.createdAt), { addSuffix: true })`, or (b) recommend using `distanceInWords(aiSummary.createdAt, false)` from `@shared/lib/time` if the bare form is desired (since `distanceInWords` already handles ISO strings and the suffix question is explicit).

- F2 [HIGH] Spec lines 68, 264 / `formatDistanceToNow` and `parseISO` described as importable from `@shared/lib/time` but they are not re-exported / The spec says "both `formatDistanceToNow` and `parseISO` are already imported in `@shared/lib/time`" (line 68) and "both are already imported in `@shared/lib/time.ts`" (line 264). This is misleading: those functions are imported BY `time.ts` for its own internal use, but they are NOT re-exported. Consumers of `@shared/lib/time` cannot import them. The exported functions are: `hoursAgo`, `timeAgoInWordsShort`, `timeAgoInWordsLong`, `prettyDate`, `formatMDY`, `prettyDateAndTime`, `prettyDateSimpleISO`, `prettyDateSimple`, `prettyTime`, `distanceInWords`, `isDeadlineDateAfterCurrent`. An implementer following the spec will get an import error. / Fix: Change the guidance to either (a) import `formatDistanceToNow` from `date-fns/formatDistanceToNow` and `parseISO` from `date-fns/parseISO` directly, or (b) use the already-exported `distanceInWords` function which accepts ISO strings and handles the `addSuffix` concern (see F1), or (c) add a new helper to `time.ts` and list `time.ts` as a modified file.

- F3 [HIGH] Spec lines 101-112 / Callout table row order contradicts stated evaluation order / Line 103 says "Evaluate in the same order as PlatoTab: when a summary exists, check status first (rows 2-3, 5-6); when no summary exists, check `hasResume` (rows 1, 4)." But the table physically lists no-summary rows interspersed with status rows: row 1 is "No summary AND has resume", row 4 is "No summary AND no resume", with status-based rows 2-3 and 5-6 in between. The PlatoTab table (lines 57-64) lists all status rows first (rows 1-4), then all no-summary rows (rows 5-6) -- the row order matches the evaluation order. The callout table's row order does NOT match the evaluation order, which will confuse implementers: the table says "first match wins" but the first row in the table (no summary + has resume) is NOT the first condition to evaluate (status === succeeded is). / Fix: Reorder the callout table to match the PlatoTab evaluation order: (1) Succeeded not stale, (2) Succeeded stale, (3) Failed, (4) Generating, (5) No summary AND has resume, (6) No summary AND no resume. Update the parenthetical row references in line 103 accordingly.

- F4 [MED] Spec line 278 / False analog reference for `<button>` reset CSS pattern / The spec says "The codebase uses this pattern in `ContentWrapper/index.js`" for the `<button>` with reset CSS pattern. But `ContentWrapper/index.js` does NOT use a button with reset CSS. It contains a standard Bootstrap button (`<button className="btn btn-round">`) inside a breadcrumb dropdown -- no reset CSS, no card-as-button pattern. An implementer looking at this analog will find no useful guidance. / Fix: Either cite a correct analog or remove the reference and say "this is a new pattern for the codebase."

- F5 [MED] Spec line 129 / `useFeatureFlipper` example uses string literal instead of `Features` enum / The spec example shows `useFeatureFlipper()({ feature: "AI_APPLICANT_SUMMARY" })` but the codebase convention for the hook is to use the `Features` enum: `useFeatureFlipper()({ feature: Features.AI_APPLICANT_SUMMARY })` (see `AccountContainer.tsx` line 45). The `FeatureFlipper` JSX component uses string literals (`<FeatureFlipper feature="AI_APPLICANT_SUMMARY">`) but the hook uses the enum. The spec's import list at line 126 already says to import `useFeatureFlipper` from the FeatureFlipper module but does not mention importing `Features`. / Fix: Change the example to `useFeatureFlipper()({ feature: Features.AI_APPLICANT_SUMMARY })` and add `Features` to the import at line 126 (it's a named export from the same module).

- F6 [MED] Spec lines 144-151 / `StyledLabel` replication instruction omits required `Box` and `Text` imports / The spec says to replicate the `StyledLabel` inner wrapper pattern from `NavItem.tsx` lines 103-118. That pattern is `const StyledLabel = styled(Box)` with a `${Text}` CSS selector inside it, which requires importing `Box` from `@shared/components/Box` and `Text` from `@shared/components/Text`. The spec mentions neither import. An implementer copying the pattern verbatim will get undefined reference errors. / Fix: Add to the sidebar section (line 138 area) that `Box` and `Text` must also be imported for the `StyledLabel` pattern.

- F7 [LOW] Spec line 266 section heading / `months_by_domain` is snake_case in section heading / The section heading says "No `months_by_domain` bar chart" using snake_case, but the corresponding field in `AiResumeStructuredData` is `monthsByDomain` (camelCase, line 30 of `aiJobApplicationSummary.ts`). - F8 [LOW] Spec line 129 / possiblePaths now dynamic but useEffect dependency unchanged / The spec says `possiblePaths` must be made dynamic (line 131: "Lines affected: 150-158 (possiblePaths -- must be made dynamic)"). Currently `possiblePaths` is a const array inside the useEffect callback (line 151), so it's recreated on every run -- no memoization issue. But the spec's example places `isAiEnabled` outside the useEffect (as a hook call, which must be at the top level). If the implementer moves `possiblePaths` outside the useEffect (a reasonable interpretation of "must be made dynamic"), it would need to be in the dependency array or wrapped in `useMemo` to avoid stale closures. Since the current code defines `possiblePaths` INSIDE the useEffect callback, the simplest correct implementation keeps it there (just change the literal array to spread `isAiEnabled`). The spec does not clarify this, leaving room for an implementer to introduce the array outside the effect. / Fix: Add a note: "Keep `possiblePaths` inside the useEffect callback (where it currently lives). Define `isAiEnabled` at the component top level (hooks cannot be called inside useEffect), then reference it inside the callback."
