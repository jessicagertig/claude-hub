# Textract-Scoring Bridge -- Round 1

## Findings

- F3 [MED] `app/models/textract_result.rb`:91-93 / `generate_ai_summary` correctly calls `AiJobApplicationAction::Orchestrate.new(textract_result_id: id).call` and is correctly moved below the `private` keyword. The `generate_ai_summary_with_credit_flow` method (line 61-82) still calls it via `generate_ai_summary` at line 67. The credit consumption gate at line 75 (`return unless ai_job_application_summary&.status_succeeded?`) correctly gates on `succeeded` which now means full pipeline complete. However, when the orchestrator returns early at `awaiting_job_criteria` (criteria not yet extracted), `generate_ai_summary_with_credit_flow` proceeds to check `status_succeeded?`, finds it false, and returns without consuming credits -- correct. When the `AiJobCriteria` `after_commit` callback re-enqueues `GenerateAiJobApplicationSummaryJob`, that job calls `generate_ai_summary_with_credit_flow` again, which calls the orchestrator, which resumes from `awaiting_job_criteria`. This path is correct but means `generate_ai_summary_with_credit_flow` is called TWICE for the same summary (once initially, once on resume). The second call will attempt credit consumption again after `succeeded`. This is safe because `CreateAiCreditBalanceTransaction` is called each time `status_succeeded?` is true -- but the existing code does not guard against double-consumption for the same summary. **This is a pre-existing pattern** (not introduced by this implementation) since the same double-call pattern existed before the scoring integration. The existing `generate_ai_summary_with_credit_flow` has no idempotency guard on credit consumption. Flagged as MED because it's pre-existing and matches the analog, but it's worth noting for the future.

No other issues found. All four entry points (auto, manual, bulk, criteria-ready callback) correctly reach the orchestrator through the same `TextractResult#generate_ai_summary_with_credit_flow` path.
