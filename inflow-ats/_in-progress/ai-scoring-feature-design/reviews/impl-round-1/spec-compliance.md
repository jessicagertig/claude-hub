# Spec Compliance -- Round 1

## Findings

- ~~F4~~ [INFO] Four frozen prompt files were created in the pre-work commit (4a7040c0b) and left untouched by the implementation (zero uncommitted changes to these files). The spec's "do not modify" constraint is satisfied -- they were committed as part of pre-work and the implementing agent did not touch them. No issue.

- F5 [HIGH] Spec Section 2 and Plan Phase I: `AiJobApplicationSummaryStatus` lifecycle -- spec says "Create when AI evaluation first kicks off for a job application." The implementation creates the status record in `CreateAiSummaryGeneration` (interactor) at two points: line 57 (`find_or_create_by` after new summary save in the textract-pending path) and line 73 (`find_or_create_by` after summary save in the textract-complete path). However, the auto-trigger path (`TextractResult after_commit -> queue_ai_summary_job -> GenerateAiJobApplicationSummaryJob`) does NOT go through `CreateAiSummaryGeneration`. It goes directly to `TextractResult#generate_ai_summary_with_credit_flow -> Orchestrate`. The orchestrator calls `Summary::Generate` which creates the summary record directly (line 35-40) WITHOUT creating the `AiJobApplicationSummaryStatus` record. This means auto-triggered evaluations (the most common path) will never have a status record created. The `update_summary_status_record` callback on `AiJobApplicationSummary` (line 53-63) has `return unless ai_job_application_summary_status` -- it silently returns if no status record exists. **Result:** For auto-triggered summaries, the `ShallowJobApplicationSerializer` will serialize `ai_job_application_summary_status` as `null`. The frontend will never know a completed evaluation exists for auto-triggered applications. **Recommended fix:** Create the `AiJobApplicationSummaryStatus` record either in `Summary::Generate` when creating a new summary, or in the orchestrator, or in the `AiJobApplicationSummary after_commit` callback (on create). The `after_commit on: :create` approach is the most robust since it catches all creation paths.

No other spec-compliance issues found. All other spec requirements are correctly implemented: status enum values and ordering, `ExtractCriteria` structural match to `Summary::Generate`, `update` vs `update_columns` for `succeeded` transitions, credit consumption timing, broadcasting timing, Flipper reuse, serializer attributes.
