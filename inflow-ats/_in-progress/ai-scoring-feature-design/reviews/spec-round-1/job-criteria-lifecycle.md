# job-criteria-lifecycle — Round 1

## Findings

- F1 [MED] `extract_job_criteria` returning on `pending` status but not `in_progress`. Section 7 says: "Find existing `AiJobCriteria` by `job_id` -- return if status `pending` (already queued)." But what if status is `in_progress`? A description change during in-progress extraction should not create a duplicate extraction -- it should either let the current one finish or queue a new one after it completes. The spec only gates on `pending`, meaning a description change while extraction is `in_progress` would build a new `AiJobCriteria` record, fail on the unique index (`job_id` unique), and `save` would return false (which the spec handles by returning). So the unique index protects against the duplicate, but the save failure path is silent -- the user gets no feedback. This works correctly but is not explicit in the spec. **Fix:** Expand the guard to return on `pending` OR `in_progress` status, or document that the unique index constraint handles the `in_progress` race gracefully.

- F2 [MED] `AiJobCriteria` overwrite on re-extraction not specified. Section 1 says "One record per job. Overwritten on re-extraction (not versioned)." But `extract_job_criteria` in Section 7 says "If not found -- build new AiJobCriteria with `job_id`." If a record already exists (status `succeeded` or `failed`), the spec says it won't be found? Actually, re-reading: the spec says "Find existing `AiJobCriteria` by `job_id` -- return if status `pending`". This implies: find the record, check status, return only if pending. If status is `succeeded` or `failed`, proceed -- which means reset status to `pending` on the existing record and enqueue. But the spec says "If not found -- build new" -- this doesn't handle the case where the record exists with `succeeded` or `failed` status. **Fix:** Clarify the flow: if existing record has status `succeeded` or `failed`, reset its status to `pending` and save (reuse the record). If status is `in_progress`, return. If no record exists, build new.

- F3 [LOW] The 2-minute delay on `ExtractJobCriteriaJob` acts as debounce, but the spec doesn't address what happens if the user saves the description multiple times in rapid succession. Each save triggers `handle_description_change` -> `extract_job_criteria`. If the existing record is `pending`, it returns (correct). If a job fires and transitions to `in_progress` between saves, F1 applies. The debounce works as described; this is just noting the edge case is handled.
