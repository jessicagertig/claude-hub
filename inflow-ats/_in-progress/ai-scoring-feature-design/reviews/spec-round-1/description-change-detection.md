# description-change-detection — Round 1

## Findings

- F1 [HIGH] `extract_job_criteria` saves an `AiJobCriteria` record inside `handle_before_update`, which runs inside the Job save transaction. If `extract_job_criteria` calls `AiJobCriteria.save` (a regular save), that save participates in the outer transaction. Then `extract_job_criteria` calls `ExtractJobCriteriaJob.set(wait: 2.minutes).perform_later(ai_job_criteria.id)`. On Rails 6.1 with Sidekiq adapter, `perform_later` pushes to Redis IMMEDIATELY (not after commit -- `enqueue_after_transaction_commit` was introduced in Rails 7.2). If the outer Job save subsequently fails (validation error, database constraint), the outer transaction rolls back, the `AiJobCriteria` record is rolled back, but the Sidekiq job has already been enqueued. When the job fires 2 minutes later, `AiJobCriteria.find_by(id: ai_job_criteria_id)` returns nil and the job returns early (the spec says "return if not found"). No data corruption, but an orphaned job runs unnecessarily.

  However, the existing pattern in `handle_before_update` already enqueues `UpdateDistributionsJob.perform_later(id)` (line 479) and `handle_status_changed_to_published` enqueues 4+ jobs via `perform_later` (lines 549-556). So this is an established pattern in this codebase, not a new risk. The `AiJobCriteria` save is the novel part -- it creates a record inside the transaction that gets rolled back. The job's guard (`return if not found`) handles this safely.

  **Fix:** Add a note to Section 7 acknowledging that `extract_job_criteria` saves a record and enqueues a job inside a `before_update` callback (inside the transaction). State that: (a) the job guards against the record not existing, and (b) this follows the existing pattern of enqueuing jobs from `before_update` in the Job model. Alternatively, consider using `update_columns` for the `AiJobCriteria` save (bypasses transaction nesting) -- but `update_columns` only works on persisted records, not new builds. Or use `after_commit` context for the enqueue.

  Downgrading to MED since the existing pattern handles this safely via the guard clause.

- F2 [MED] `description_meaningfully_changed?` strips "all non-alphabetical characters." This removes numbers. A job description changing salary from "$100,000" to "$200,000" or experience from "5 years" to "10 years" would not be detected as a meaningful change if only the numbers differ. This may be intentional (numbers alone don't change criteria), but if a JD changes "5+ years of experience" to "10+ years of experience", the criteria tier could be different. **Fix:** Document explicitly that numbers are intentionally excluded from the meaningful change comparison, or change the filter to preserve digits.

- F3 [LOW] The spec says `handle_description_change` checks `description_changed?` AND `published?` AND `description_meaningfully_changed?`. The `description_changed?` is a Rails dirty method that works in `before_update` (because the model is dirty but not yet saved). The `published?` check is a status check. If the description changes AND the status simultaneously changes from draft to published, both `handle_status_changed_to_published` (which calls `extract_job_criteria`) and `handle_description_change` (which also calls `extract_job_criteria`) would fire. But `extract_job_criteria` guards against duplicates via the `pending` status check, so the second call returns early. No issue, just noting the interaction.
