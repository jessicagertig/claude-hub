# concurrency-and-race-conditions — Round 1

## Findings

- F1 [MED] `AiJobCriteria` `after_commit` callback must use `update` (not `update_columns`) for the `succeeded` transition. The spec says `ExtractCriteria` follows "the same pattern as `AiJobApplicationAction::Summary::Generate`" for error handling and status transitions. But `Summary::Generate` uses `update_columns(status: :failed, ...)` for failure transitions (lines 174, 179, 183) -- `update_columns` bypasses callbacks. If `ExtractCriteria` follows this pattern for the `succeeded` transition too, the `after_commit` callback that resumes waiting summaries would never fire. The spec must explicitly state that the final `succeeded` transition on `AiJobCriteria` must use `update` (not `update_columns`) to trigger the `after_commit` callback. **Fix:** Add to Section 4 under `ExtractCriteria`: "The final `succeeded` status transition must use `update` (not `update_columns`) to ensure the `after_commit` callback fires."

- F2 [LOW] Multiple waiting summaries: the `after_commit` callback finds all `AiJobApplicationSummary` records for the job with `awaiting_job_criteria` status and enqueues a job for each. If 50 candidates applied to the same job, this enqueues 50 `GenerateAiJobApplicationSummaryJob` jobs simultaneously. This is acceptable behavior (each runs independently for a different candidate), and the Sidekiq `:default` queue will process them in order. No issue, just noting scale.

- F3 [LOW] The spec doesn't address what happens if `ExtractCriteria` fails. The `after_commit` callback only fires on `succeeded`. If criteria extraction fails, waiting summaries remain at `awaiting_job_criteria` indefinitely. The spec should document the expected behavior: either the summary eventually times out, or the user manually retriggers, or the criteria failure is surfaced. This is not blocking because the failure scenario doesn't break anything -- summaries just wait -- but should be documented.
