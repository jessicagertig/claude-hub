# pipeline-status-lifecycle — Round 1

## Findings

- F1 [HIGH] `Summary::Generate` final status not specified for new enum. The existing `Summary::Generate` (app/services/ai_job_application_action/summary/generate.rb line 163) sets `status: :succeeded` as its final status. With the redesigned enum, `succeeded` means full pipeline complete (summary + scoring + integration). The spec says the orchestrator calls `Summary::Generate` as step 1, but never states what `Summary::Generate`'s final status should now be. It should transition to `summarizing` (or the orchestrator should advance the status after `Summary::Generate` returns). Without this, `Summary::Generate` would set `succeeded` prematurely, triggering credit consumption and the `destroy_previous_textract_results` callback before scoring starts. **Fix:** Add explicit statement that `Summary::Generate` must be modified to set its final successful status to a pre-scoring status (the orchestrator advances to `awaiting_job_criteria`/`scoring` after Generate returns). Alternatively, state that the orchestrator handles the post-summary status transition.

- F2 [HIGH] `Summary::Generate` uses `status_in_progress?` and `status: :in_progress` -- but `in_progress` is removed from the new enum. Lines 31-32 of generate.rb check `status_pending?`, `status_textract_processing?`, `status_in_progress?` and set `status: :in_progress`. In the new enum, `in_progress` does not exist -- the equivalent is `extracting: 2`. The spec does not enumerate the changes needed in `Summary::Generate` for the new enum values. **Fix:** Add to Section 3 or Section 5 an explicit list of status references in `Summary::Generate` that must be updated: `status_in_progress?` -> `status_extracting?`, `status: :in_progress` -> `status: :extracting`, and the final `status: :succeeded` -> (see F1).

- F3 [MED] Resume points incomplete. Section 5 lists resume points for `extracted`, `awaiting_job_criteria`, and `scoring`. Missing resume points for `extracting` (Call 1 in progress -- should restart from Call 1 or fail?) and `summarizing` (Calls 2-4 in progress -- should restart from Calls 2-4?). If the pipeline crashes mid-extraction or mid-summary, the orchestrator needs to know what to do. **Fix:** Add resume points for `extracting` and `summarizing` (or state that these are considered failed-and-retried by the sub-service's own error handling).

- F4 [MED] `textract_processing` integer value change (6 -> 1) not called out. The existing `textract_processing: 6` moves to `textract_processing: 1` in the new enum. While the spec says "rollback the existing migration and edit in place," it does not highlight that `textract_processing` changes integer value. Any raw integer references (e.g., `status: 6` in raw SQL or test fixtures) would break silently. The spec's instruction to rollback-and-edit is correct since the feature is not in production, but a note about data implications would prevent confusion. **Fix:** Add a note under Section 3 that ALL integer values are renumbered and any raw integer references to status values in tests or utilities must be updated.

- F5 [LOW] The `failed: 9` status allows no room for future intermediate states between `integrating` and terminal success. Not blocking -- the spec already notes "This enum may require adjustment when wired into the full application flow."
