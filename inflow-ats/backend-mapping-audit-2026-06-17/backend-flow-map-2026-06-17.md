## Overview

This document traces every code path for both Textract resume processing and AI applicant summary generation, from trigger to final result. Both flows are interconnected: Textract extracts text from resumes, and AI summaries consume that text through a multi-stage AI pipeline (4 summary calls + 1-5 scoring calls + 1 display call + 1 integration call). The bridge between them is the `TextractResult#queue_ai_summary_job` after_commit callback.

The most consequential change since the prior map is the **`AiJobApplicationSummaryStatus` record**: it is no longer a 10-value mirror of the summary pipeline. It is a 4-value display-state record (`none`/`initial_summary_pending`/`current`/`regenerating`), created and advanced by a dedicated interactor (`FindOrCreateAiJobApplicationSummaryStatus`) and a helper (`TextractResult#set_initial_summary_pending`), owned by the unconditional owner `JobApplication` rather than by individual summaries. It backs the job-applications list fit indicator. A full dedicated section appears in **Part 9**.

## Part 1: Textract Resume Processing Flow

### Core Service Chain

```
[Trigger] → SubmitResumeToTextractJob → SubmitResumeToTextract#submit_resume
  → AWS Textract API (async job created)
  → (conditional) marks ALL existing summaries stale:true via update_all
  → TextractResult record built+saved (status: in_progress)
  → If a textract_processing+stale:false summary exists with nil textract_result_id:
      update_columns(textract_result_id:) on it
  → GetResumeTextFromTextractJob (scheduled +2 min)
    → GetResumeTextFromTextract#parse_resume_text
      → AWS Textract API (poll for result)
      → TextractResult updated with extracted text (status: succeeded via .update)
        → fires after_commit :queue_ai_summary_job (the AI bridge)
      → On retry exhaustion: cleanup_orphaned_summary destroys any
        textract_processing summary + AI_SUMMARY_FAILED broadcast
```

## Part 4: Cleanup and Failure Handling

- **Textract retry exhaustion:** `cleanup_orphaned_summary` destroys the `textract_processing` summary + `AI_SUMMARY_FAILED`. No-op without a waiting summary.
- **Resume replacement cascade:** conditional `update_all(stale: true)`; new `in_progress` TextractResult; prior TextractResult NOT destroyed here; status row untouched by `SubmitResumeToTextract`. On the new result succeeding with auto-gen ON, the status row is flipped to `regenerating` and sticks there (S-D / T2).
- **Summary success cascade:** `destroy_previous_textract_results` (earlier non-succeeded TextractResults) + `update_summary_status_record` (status row → `'current'`).
- **Bulk batch failure (whole-batch):** `discard_on StandardError` and `retry_on CustomErrorAiSummary` exhaustion both call `update_remaining_statuses_to_failed` (flips remaining `:processing` rows to `:failed`) + `notify_failure` (`bulk_generate_ai_summaries_job.rb:12-21,175-182`).
- **Bulk batch failure (normal on_complete):** `on_complete` does NOT call `update_remaining_statuses_to_failed`, but when `succeeded.zero? && failed.positive?` (`:113-114`) it still calls `notify_failure` (broadcasts `AI_SUMMARY_BULK_FAILED` + failure mailer) WITHOUT flipping any `:processing` row. A per-row validation-failure or non-CustomError rescue can therefore leave a row stuck `:processing` while being counted `failed` by subtraction.
- **Bulk empty working set:** no job enqueued, no `on_complete`, no broadcast or mailer; the only signal is the synchronous controller JSON.
