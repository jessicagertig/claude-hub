# Iterative Adversarial Spec Review

You are running iterative adversarial review on a feature spec. Goal: drive the spec to TWO CONSECUTIVE FULL PASSES — two rounds in a row that produce ZERO new BLOCKER or HIGH findings AND require ZERO spec amendments. Stop when that criterion is met, or after 5 rounds (whichever comes first).

## Ground rules

- You are NOT writing code. You are reviewing spec text against the live source tree (path in `REPO-PATH` in the working directory). Read-only.
- Apply amendments IN-LINE to the spec file as you find issues.
- Read the pipeline's CLAUDE.md for safety rules and conventions.
- If a conventions sources exists (named in the pipeline CLAUDE.md), read the relevant files.
- When dispatching sub-agents, keep scope narrow and file lists explicit.
- If you need to abandon a review angle because it's unverifiable, state so explicitly. Do not speculate.
- DO NOT re-open issues already closed in prior rounds. Read prior round directories first; treat their findings as the baseline and only add NEW observations.

## Directory structure

All review artifacts go under `reviews/` in the working directory:

```
reviews/
└── spec-round-1/
    ├── <angle-slug>.md
    ├── <angle-slug>.md
    └── verdict.md
```

Create `reviews/` on your first round. Create `reviews/spec-round-N/` at the start of each round. Write one file per angle as you complete it. Write `verdict.md` last, after all angles are done.

## Inputs (read these first, in order)

1. The spec file in the working directory (SPEC.md)
2. `approved-decisions.md` if present — the decisions that shaped the spec
3. `reviews/spec-round-*/` if present — prior rounds already run. Read the `verdict.md` in each.
4. The pipeline CLAUDE.md and conventions sources (if any)

## Before starting Round 1: Plain English Summary + Blast Radius

Before running any review angles, produce a summary:

### Plain English Summary
In 1-2 paragraphs, no jargon, no identifiers: what is this feature doing and why? Write it so someone who doesn't read code can gut-check whether the approach makes sense.

### Blast Radius Analysis
For every part of the system this spec touches, answer:
- What existing behavior changes?
- What existing code needs to be modified?
- What callers, consumers, or downstream systems are affected?
- If this is wrong, what breaks? One component? One workflow? The whole app?

Present both, then proceed to Round 1.

## Adversarial angles

Read `reviews/REVIEW-ANGLES.md` for the review angles specific to this feature. That file was generated by a prior agent and reviewed before this session.

Each round MUST address every angle listed, including all always-on checks that apply. Miss an angle and the round doesn't count toward the two-consecutive-pass criterion. Use the angle slugs as filenames.

## Per-round procedure

### Step 1: Create the round directory
Create `reviews/spec-round-N/` for this round.

### Step 2: Re-read the spec
Always re-read the spec at the START of each round. You may have amended it in the previous round; review the AMENDED text.

### Step 3: Work each angle
For each angle in `reviews/REVIEW-ANGLES.md`, write a file in the round directory using the angle's slug as the filename:

```
# [Angle Name] — Round N

## Findings
- F1 [BLOCKER] where (file:line or identifier) / what / evidence / fix
- F2 [MED] ...

## Amendments Applied
- spec line N-M: summary of edit

(If no findings: "No issues found.")
```

### Step 4: Apply amendments to the spec
For every BLOCKER and HIGH finding, apply the concrete fix to the spec now. Verify the edit by re-reading the patched section.

### Step 5: Write the round verdict
Write `reviews/spec-round-N/verdict.md`:
```
# Spec Review — Round N Verdict
**Date:** YYYY-MM-DD HH:MM

## Counts
- BLOCKER: N
- HIGH: N
- MED/LOW: N

## Amendments Applied
- [summary of each amendment]

## Verdict: PASS | FAIL
```

### Step 6: Decide loop continuation
- If this round produced 0 BLOCKER and 0 HIGH and required 0 amendments, mark it PASS.
- If the previous round ALSO passed, STOP. Declare TWO CONSECUTIVE FULL PASSES.
- Otherwise, start the next round.
- If round count reaches 5 without two consecutive passes, stop and escalate with the remaining gaps.

## Termination output

When the loop ends, write `reviews/SPEC-REVIEW-COMPLETE.md` containing:
- Final verdict (READY FOR PLANNING vs ESCALATE)
- The plain English summary + blast radius analysis (updated if amendments changed scope)
- Summary of each round's outcome (one line per round with verdict and finding counts)
- Any remaining open questions

## Escalation conditions — stop immediately and present to the user

- A BLOCKER that requires fundamental redesign, not just spec-text edits. Do not attempt to fix; present.
- Evidence that a prior round's amendment was incorrect. Roll back the bad amendment; then present.
- Repo state has drifted (new commits affecting scope). Check `git log --oneline` on relevant files. If drifted, present.
- Permission system blocks a needed verification.

## What success looks like

The spec survives two consecutive reviews across all angles with no required amendments. `reviews/SPEC-REVIEW-COMPLETE.md` declares READY.

## What failure looks like

After 5 rounds, still finding BLOCKER/HIGH issues. Write a clear escalation note: list the unresolved issues, what you tried, what you recommend doing next.
